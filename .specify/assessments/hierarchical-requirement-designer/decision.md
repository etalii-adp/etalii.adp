## Verdict & Rationale

**Go.** The three conditions for a go are met: the problem is valid (adequate), the evidence is adequate, and a concept is shaped and chosen. A `needs-clarification` would name questions, and the ones still open about the problem (what the present way costs, whether the hierarchy helps, how often agents break the structure, how large a document grows) are not questions the maintainer can answer: `problem.md` records each as something only a trial or use would measure, and the maintainer has decided against the trial. Sending the idea back to an earlier stage would return it unchanged. A `kill` would rest on value against cost, the one criterion rated weak, and that weighing is the maintainer's to make: the maintainer is the one who raises, decides and builds, is the tool engineer who carries the cost of the specification changes, and has made the weighing twice with the objection in view. The idea fits what ADP is for, and nothing in the artifacts shows it to be wrong; they show it to be unproven.

Three reservations are part of this decision and are to be read with it:

- **The scorecard supports Option B better than Option C.** B meets every goal in `problem.md` and changes one specification; C changes four and adds a state, sorting and a managed category list that have no goal or metric behind them. The go hands off C because the maintainer chose it knowingly, not because the evidence prefers it. What C adds over B is where the specification should be most ready to cut.
- **The go does not pass the constitution check.** The Markdown family in FBL and the block in the registration each still have to be justified on the plan as a current tool's need and as the simplest construct that meets it (principle V), and each comes as a document, a schema and worked examples together (principle II). If the plan cannot justify them, the fallback is on record: Option B's persistence plugin and the registration as it is.
- **No evidence is gathered before the specification is written.** With the trial declined, the baseline for the time metric, the count of agents' breaks and the shape of a real document in the layout are found by the specification and by use. The answer for depth has to be settled in the specification before the surface kind is written down, since every host must then implement it.

This decision is revisited if the open work on the standalone host leaves a host on which a second designer cannot be built without redoing it, or if the plan's constitution check refuses the changes Option C rests on.

## If go — Handoff to `/speckit-specify`

Not before the open work on the standalone host is done, spec 025-standalone-code-structure among it; the maintainer placed this after that work.

- **Problem**: A person who works with agents on requirements has them only as flat, per-feature Markdown that the agent reads and writes, which the person can only skim and search as text; that is slow and does not show how the requirements fit together, and there is no one place that follows the subject's structure in which the two can discuss them.
- **Chosen approach**: Option C of `concept.md`, the idea in full. A designer type that users see as "Hierarchical Requirement Designer", first in the standalone host, over a Markdown file of nested bullets that is the designer's own document and that the agent keeps reading and writing as text. A hierarchy level carries `ITEM-000x` and a requirement `REQ-000x`, each counted up in its own list, given once by the tool and never changed. The person sees one document that scrolls from top to bottom: hierarchy levels as boxes with what they contain to their right, a title and an optional description on each level and requirement, collapsing, tags below the title from a managed list that behaves as Notion's selection property does, an assessment icon that opens an editable list, and references picked after typing a `#` and shown as a box in the text. With it: a category from a list the user can change, a state on a requirement, sorting, wildcard filtering on hierarchy levels and stored filters; nested Markdown bullets as a family FBL can declare; and a block in the registration for a tool's settings, the tag list's colours and order among them. A document the tool creates is filled with a starting structure of at most two levels, at most three requirements on each, and a legend for the agent. File interaction is FBL's: a changed file is read again and the difference taken by id, a bullet the designer cannot follow is a finding on that bullet, an unreadable body is read-only with one finding.
- **In scope / out of scope**: In scope is everything above, for any subject requirements are drawn up for, with the looks of the Knowledge designer. Out of scope: hosts other than the standalone host; showing how requirements connect beyond a reference from one to another; taking the text away from the agent; the Knowledge designer beyond its looks; getting agents to write less requirement text; Spec Kit's `spec.md` and spec-workflow's `requirements.md`, which are neither read nor replaced; references that leave the document, for the initial version; merging the edits of two writers; rich text in a description beyond the reference box; Option A's trial.
- **Success metrics**: Confirmed: the time a person needs to find and judge the requirements of one part of a subject and to see how they fit together with the rest (baseline not measured); a second user, someone other than the maintainer, adopts it (baseline none; it adds to success and is not a condition for it). Candidates to confirm in the specification: the share of an agent's changes a person can follow without an error and without repairing the file by hand; the number of references that still point at the same requirement after a reorganisation; the maintainer keeps the requirements of at least one real subject outside this repository this way and prefers it to the text.
- **Carried-forward open questions**:
  - How the work is cut into features. Spec Kit asks for one feature per change to a specification, and Option C changes DESL (a second surface kind, a counted identifier), FBL (a Markdown family, a registration block) and what DED says of a Markdown document, beside the tool type's definition here and its implementation in the standalone host, which plans with spec-workflow in its own repository.
  - Whether the plan can justify the Markdown family in FBL and the registration block under principle V, and whether a second tool is in view that would bind its Markdown through the family.
  - The layout in the width, for a hierarchy with no maximum depth in which every level stands to the right of the one that contains it; where requirements stand relative to sub-items. To be settled before the surface kind is specified.
  - The envelope, the origin identifier and the file extension (a plain `.md` registered through Add, or an extension of its own).
  - How the file is written: a category, a state, a description and what sets it off from the title, the prefixes, a tag's anchor and a reference's link (the `#` as key or as notation), a hierarchy level's tags, the part for assessments, prose outside the bullets, and which faults make the body unreadable as a whole.
  - Numbering: when the tool numbers an entry written as text, what it does with a number the writer chose or that clashes, the number of digits, whether the counts are kept per file and where, and that a deleted number is not given out again.
  - The tag list: what goes in the registration (colours, order, what is collapsed, stored filters) and what in the Markdown, what an agent that adds a tag as text has to do, what renaming or deleting a tag does to its carriers, and how a partial or differently cased match resolves.
  - Assessments: the kinds, whether one attaches to a hierarchy level directly or to the file, how far one reaches up the hierarchy, what resolving and acting on one comprise, whether an agent can do either, and what becomes of a resolved one in the file.
  - Categories (the full default list), states (which exist, who sets one), sorting (of what, by what, stored or not) and the wildcard syntax.
  - References: plain link or relation with a kind, a link an agent wrote that points outside the document, and what happens to a link or an assessment that names something deleted.
  - The quick ways to add, moving by drag and drop, whether the numbers are shown, and what the looks taken from the Knowledge designer comprise for parts it does not have.
  - How large one document is expected to grow, and whose requirements, of which subject outside this repository, are the first to be kept this way.
  - Unmeasured and left to use: what the present way costs, how often agents break the structure, and whether the layout makes a person faster.
