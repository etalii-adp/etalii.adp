# Idea Research: Hierarchical Requirement Designer

- **Slug**: hierarchical-requirement-designer
- **Created**: 2026-10-13
- **Evidence confidence (overall)**: medium

What the specifications and the standalone host say today is well evidenced (read from the files, cited by path). Who wants this besides the maintainer is not: the demand is one stated want. The external evidence is mostly repository front pages and one practitioner article, enough to place the idea among its neighbours, not to size a need.

The idea changed after this research was first written: on 2026-10-13 the maintainer replaced `REQ-x.y.z` by `REQ-000x`, a number that never changes, also when the requirement is moved (intake, clarification on how a requirement is identified). The findings that rested on the earlier shape are rewritten below for the idea as it stands, and say where the change answers them.

Paths without a repository are in `etalii.adp`; `standalone:` marks a path in `etalii.adp.ide.standalone`, read at commit `1a8e66e3e` on `develop`. A line number marked `~` was counted from a section start.

## Prior Art

### In this organization

- **Agent Behavior Modelling (`etalii/agent-behavior-modelling`) already is a tool over nested Markdown bullets that an agent reads.** A node is one list item, `- **<Keyword>:** <label>`; children are the items indented under it; lines under an item that are not items are its notes; everything outside the list "is the author's ... and is neither modelled nor touched". It is a diagram, state Prototype, in the standalone host and the VS Code plug-in. It matters because it settles, for one tool, most of what the intake leaves open for this one, and settles two points the other way (next two findings). — [source: `definitions/diagrams/agent-behavior-modelling.md` lines 11-14, 44-63; `standalone:src/diagrams/agent-behavior-modelling/backend/EtAlii.Adp.Diagram.AgentBehaviorModelling/AbmParser.cs:11-16`] (confidence: high, cited)
- **It deliberately writes no identifier into the Markdown**: "Nothing is written into the Markdown to name a node, because anything written there the agent would read too." Its ids are places in the tree (`1`, `1.2`, `1.2.1`), and the price is recorded as "a known limit": a reorder or a re-parent changes a node's id, and what was stored under the old id follows the place, not the node. The intake chooses the opposite on both counts, for hierarchy levels and requirements alike (`ITEM-000x` and `REQ-000x`, written into the file, never changing): it avoids the known limit, and takes on what that tool avoided, identifiers the agent reads. — [source: `definitions/diagrams/agent-behavior-modelling.md` line 59] (confidence: high, cited)
- **Its Markdown is read by a persistence plugin, not a declared binding**: "FBL's declarative readers cannot find a tree inside someone else's prose". The plugin plans add, set, remove, move and retype as line splices; the host keeps registration, undo, drift and the byte-preserving write. Its parser is hand-written (321 lines) and reads one list under one heading; the standalone backend has no general Markdown parser. — [source: `definitions/diagrams/agent-behavior-modelling.md` lines 46-48; `specifications/fbl/FBL-specification.md` section 11.2; `standalone:src/diagrams/agent-behavior-modelling/`] (confidence: high, cited)
- **How it tells its `.md` from any other**: `.md` is a shared extension, and "a `.md` file becomes one only when the user registers it through Add, which writes the `.adp`". A new file is written with a legend section that tells the agent what each keyword means: "The legend is what lets a model that has never heard of behavior trees follow one." Both bear on the intake's open questions on the file extension and on what an agent needs in order to read the file. — [source: `definitions/diagrams/agent-behavior-modelling.md` lines 62-63] (confidence: high, cited)
- **The Knowledge designer (`etalii/knowledge`) is the one designer there is**, state Prototype, delivered by spec 013 (status completed). It has tags (`multipleSelection`, drawn as rounded tags in their option's colour), a searchable list that also creates ("typing a name that is not an option and confirming creates the option"), renaming, recolouring, reordering by dragging and deleting of options, filters with nested groups, grouping, and a parent relation that nests rows to any depth. Much of what the idea asks of tags and filtering exists there as behaviour and as client components. — [source: `definitions/designers/knowledge.md` lines 107-124, 190; `standalone:src/client/src/table/library/`; `specs/013-knowledge-designer/.spec-context.json`] (confidence: high, cited)
- **It stores the tag list and its colours in the document, and nothing in the `.adp` file.** Options with their colours are entries of the property in the YAML, JSON or XML file, and its registration is two lines: "It SHALL hold no property, row, view, width, position or other setting, and the designer SHALL work the same after the registration is deleted and created again." The intake's rule (tags and colours in the `.adp` file) is the opposite choice. — [source: `definitions/designers/knowledge.md` lines 39, 402; `standalone:.spec-workflow/specs/knowledge-designer/requirements.md:~158` (R2.2); `standalone:src/examples/designers/knowledge/yaml/cities.adp`] (confidence: high, cited)
- **Two tools already state "people and agents on one file" as requirements.** Knowledge R8, "Readable and writable by people and by language models": a hand-written entry without an id is shown, reported at info and given an id on the first edit; the companion document must describe the file "completely enough to write a valid one by hand". Agent activity diagram R8, "Agents write it, people watch it", ships an instruction text an agent can be given, and defaults to agents editing the file directly. — [source: `standalone:.spec-workflow/specs/knowledge-designer/requirements.md:~249-259`; `standalone:.spec-workflow/specs/agent-activity-diagram/requirements.md:258-271`] (confidence: high, cited)
- **Requirements as a hierarchy were noted before, in research, not as a tool.** The technology assessment research lists a values hierarchy (van de Poel: "a value is specified into norms and norms into design requirements") as a candidate diagram, and an expectations register as a candidate designer. Neither became a feature. — [source: `docs/research/constructive-technology-assessment.md` lines 201, 308, 312] (confidence: high, cited)

### The file interaction patterns of the standalone host

The intake leaves these to "the ones as in use in etalii.adp.ide.standalone". What that turns out to be:

- **A changed file is noticed by a file watcher and re-read whole; the difference is taken on the model, not on the text.** Diagrams diff elements by id and send add, remove and update deltas; the Knowledge designer replaces its reading and pushes everything; the FBL library says "Re-reading after every edit, rather than patching the model, keeps one code path for what a body means". No code attributes an external change to a byte range or a line. So "it is detected which part of the file changed" holds in the standalone host as "which elements changed", and only where elements have ids that survive the change. — [source: `standalone:src/backend/EtAlii.Adp.Diagram/DiagramDiff.cs:8-67`; `standalone:src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeSession.cs:514-577`; `standalone:src/backend/EtAlii.Adp.Specification.Fbl/History/OpenBody.cs:8-10`; `standalone:docs/architecture.md:46`] (confidence: high, cited)
- **The host's own writes are byte-preserving splices; what a tool does not model is kept.** "A document ADP did not change MUST come back unchanged from a round trip. Constructs a module does not model are preserved, not dropped." FBL: "Reading never fails on content. What cannot be read becomes a finding; what is not bound is kept." For prose the structure has no place for, the existing answer is therefore: keep it byte for byte, and report it where the binding says so. — [source: `standalone:.specify/memory/constitution.md:45-46`; `specifications/fbl/FBL-specification.md` sections 1.4, 7.4; `specifications/ded/DED-specification.md` section 3] (confidence: high, cited)
- **What is shown while a file is in error differs between tools and between specification and code.** FBL section 7.3: a reload that finds the body unreadable "keeps the last readable model on screen, read-only, with the finding". FBL section 7.5: an unreadable body "opens as an empty, read-only model with one finding". The Knowledge designer's code shows an empty, read-only table with the reason on a malformed file, also after a reload; the agent activity diagram "keeps showing what it last read". A file that reads but holds unreadable entries still opens, each entry a finding. — [source: `specifications/fbl/FBL-specification.md` sections 7.3, 7.5; `standalone:src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeBody.cs:32, 44-47`; `standalone:src/diagrams/agent-activity-diagram/backend/EtAlii.Adp.Diagram.AgentActivityDiagram/AadSession.cs:78-90`] (confidence: high, cited)
- **Two writers are handled by refusing, not merging.** An edit is written against the file as it is on disk at that moment, or refused ("The file has changed since this edit was made, so it was not written."); undo after an external change is refused; there is no lock, no three-way merge. The code names the cost for a file agents write often: "it is a lost update a day", and "Closing it needs a lock every writer honours, which an agent with a text editor does not." The edit must "find what it edits by identity rather than by position". — [source: `standalone:src/backend/EtAlii.Adp.Documents/WritableDocumentLifecycle.cs:186-243`; `standalone:src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeBody.cs:105-109`; `specifications/fbl/FBL-specification.md` sections 1.5, 7.2] (confidence: high, cited)
- **ADP's own data goes in a sidecar only when the file belongs to another tool**: "where ADP's own data goes when the format has no place for it - a sidecar, never an annotation smuggled into a file another tool owns." The rule is written for bodies ADP does not own; this designer's Markdown is its own document. — [source: `standalone:.spec-workflow/steering/tech.md:50`] (confidence: high, cited)

### Elsewhere

- **Requirements as plain text under version control is an established, small niche, and none of its tools stores Markdown.** Doorstop keeps one YAML file per item, links items across documents that form a tree, publishes HTML, and has no editing surface on its front page (680 stars, LGPLv3). StrictDoc keeps one `.sdoc` file per document with `[REQUIREMENT]` blocks and hand-written `UID`s, and serves a local web interface (412 stars, Apache 2.0). rmToo reads requirements from text files and generates documents and dependency graphs (232 stars, GPLv3). — [source: github.com/doorstop-dev/doorstop, github.com/strictdoc-project/strictdoc, github.com/florath/rmtoo] (confidence: high for what the pages state, cited) Sphinx-Needs, reStructuredText inside Sphinx, is known here from a search summary only. — [UNVERIFIED — search summary only] (confidence: low)
- **The formats agents are given today are Markdown with headings, flat per feature or capability, and unnumbered or numbered per file.** OpenSpec: "Plain Markdown — requirements with concrete scenarios, no special syntax to learn", with `### Requirement: <name>`, `SHALL` wording and `#### Scenario:` headings, requirements identified by their heading. Kiro: three files per spec, `requirements.md` holding "user stories, acceptance criteria, or bug analysis in structured notation", tasks tracing back to requirement numbers. Spec Kit: one feature folder per change. None presents an application-wide hierarchy with requirements at every level, and none shows requirements other than as text. — [source: github.com/Fission-AI/OpenSpec; kiro.dev/docs/specs/; martinfowler.com article; github.com/github/spec-kit] (confidence: medium, cited; front pages and one article)
- **Tools that put a non-text surface on agent-written Markdown exist, for review and not for structure.** human-review (comments and edits sent back to the agent, 1.4k stars) was fetched. Roughdraft (comments kept in the `.md` as CriticMarkup), MRDown (shows what an agent's rewrite changed, three-way choice where both sides touched the same lines) and an experimental hybrid Markdown editor in VS Code are known from a search summary only. — [source: github.com/petergyang/human-review; the rest UNVERIFIED — search summary only] (confidence: medium for the first, low for the rest) No tool was found that presents a requirement hierarchy in Markdown as forms; one search was run, so this is weak evidence of absence. — (confidence: low)
- **An outliner over nested Markdown bullets at scale is Logseq** (45.2k stars, AGPL-3.0), which now introduces a "Database version" beside its file graphs, in beta, with the warning that "data loss is possible". Its front page does not say why. — [source: github.com/logseq/logseq] (confidence: medium for the facts, cited; the reason is not evidenced)
- **A hierarchical number as a requirement's identity is a known trap.** An issue raised against SysML, "Requirement ID should be immutable" (29 May 2015): "a hierarchical ID will necessary change when the hierarchy is refactored", which breaks traceability; it proposes two identifiers, "The unique and immutable Id of the requirement" and "A unique hierarchical identifier, used to organize requirements within a package". It was closed as out of scope for SysML 1.7 and deferred to SysML v2, so it is an argument on record, not a standard. The idea as changed on 2026-10-13 follows the first half of that proposal (`REQ-000x`, immutable) and has no hierarchical identifier beside it: a requirement's place is read from the nesting of the bullets. — [source: issues.omg.org, SYSML17-142; intake] (confidence: medium, cited) The same practice (assign once, never renumber, never reuse) appeared in a search summary of tool guides. — [UNVERIFIED — search summary only] (confidence: low)
- **Notion's select and multi-select property**, which the intake names as the model for tags: "prompted to add tags by typing what you want and pressing enter after each"; colours are "randomly assigned"; "Edit tag names and colors, or delete them by clicking on the property field"; "Reorder tags by grabbing the `⋮⋮` icon to their left and dragging"; "as many unique tags ... as you want". The page does not say how a partial or differently cased match resolves, or what happens to entries that carry a deleted option. — [source: www.notion.com/help/database-properties] (confidence: high for what is stated, cited)

## Market & Context

- What users rely on today is the text itself: `spec.md`, `requirements.md` and the like, read in an editor or a Markdown preview, discussed with the agent in chat. In this organization that is Spec Kit here and spec-workflow in the standalone host. — [source: `CLAUDE.md`; `standalone:.spec-workflow/`] (confidence: high, cited)
- The practice is moving towards more of it. Böckeler distinguishes spec-first (written before the work), spec-anchored ("kept even after the task is complete") and spec-as-source ("only the spec is edited by the human, the human never touches the code"), and judges Kiro and Spec Kit mainly spec-first. A document that describes a whole application by its hierarchy and is kept is a spec-anchored document, which the popular tools do not yet aim at. — [source: martinfowler.com article] (confidence: medium, cited)
- The cost of doing nothing, for the maintainer, is that requirements stay as flat, per-feature Markdown without one place that follows an application's structure. Nothing recorded says what that costs in time or mistakes. — [ASSUMPTION] (confidence: low)
- The standalone host's own Markdown editor (preview, heading outline) already opens any such file; an outline of headings is the nearest existing non-text view. — [source: `standalone:src/editors/markdown/client/MarkdownEditorPanel.tsx:30-38`] (confidence: high, cited)

## Data & Constraints

- **DED has no Markdown form.** The envelope (`ded`, `designer`) is defined for YAML, JSON and XML; for anything else: "A designer type whose bindings read another format **MUST** state in its DESL specification where the envelope is written, as the header of its binding (FBL section 5.6), and **MUST** write both values." The door is open, and it requires both values to be written in the file. This is the answer to the intake's first unknown as far as the specifications go. — [source: `specifications/ded/DED-specification.md` section 2] (confidence: high, cited)
- **DESL 0.1 has one surface.** "`kind` | `\"table\"` | **Required.** The layout. DESL 0.1 defines one kind." A form-based structure that follows a hierarchy is not a table of rows, columns and cells, so the idea needs a second surface kind or an extension of the first. — [source: `specifications/desl/DESL-specification.md` sections 7.1, 7.2] (confidence: high, cited)
- **DESL 0.1 has no counting id.** Its strategies are `uuid-v4`, `uuid-v7` and `derived`; `derived` ids are recomputed in every transaction and "the runtime **MUST** rewrite every reference to it in the same transaction". A hand-written id "**MUST** be accepted whatever the strategy". `ITEM-000x` and `REQ-000x` (counted up, never changing) fit none of the three as written: they are not UUIDs, and a `derived` id is recomputed from the model where these must stay as given. The nearest existing rule is that a hand-written id is accepted, which covers reading them and not giving out the next one. — [source: `specifications/desl/DESL-specification.md` section 5.3] (confidence: high, cited)
- **FBL has no Markdown family.** Its families are `yaml`, `json`, `xml`, `lines` and `blocks`; `lines` has no nesting and `blocks` nests by braces. "FBL is not a general grammar formalism." Nested bullets therefore mean a persistence plugin, as Agent Behavior Modelling has, or a change to FBL; "A format FBL can declare **SHOULD** be bound rather than read by a plugin." — [source: `specifications/fbl/FBL-specification.md` sections 1.5, 4.6, 4.7, 11.1] (confidence: high, cited)
- **The `.adp` registration has no place for a tag list today.** It holds the origin, the headers `body`, `view` and `resource` plus those a binding declares, and the blocks `layout:` and `identities:`; "Other view data (sizes, waypoints, label offsets) is not stored in FBL 0.1." Unknown headers are kept and reported as `fbl.unknown-header`; anything after the blocks is kept as unbound content. It is one file per document, beside it. So a tag list in the `.adp` file is a list per document, and needs a new block. — [source: `specifications/fbl/FBL-specification.md` sections 8.1, 8.3] (confidence: high, cited)
- **The constitution sets the price of each of those changes**: a normative document, a schema and worked examples together (principle II), justified "by a current tool's need, not an anticipated one" (principle V). The example validator reads designer example documents "in YAML, JSON or XML". — [source: `.specify/memory/constitution.md` principles II, V; `CLAUDE.md`, Writing specifications] (confidence: high, cited)
- **Standalone first, and the specification still comes first.** "Every host MUST implement it rather than define its own variant" (principle I); the standalone host plans with spec-workflow in its own repository, so the designer type's definition would be specified here and its implementation planned there. — [source: `.specify/memory/constitution.md` principle I, Structure and Naming] (confidence: high, cited)
- **Terminology.** A designer is "A form-based visual layout ... nothing in it is connected", and "A designer may hold relations as values and stays a designer". References between requirements shown as links in text are values, so the idea passes the test for a designer as written. — [source: `docs/terminology.md`, Tools] (confidence: high, cited)
- **Scale of what it competes with for attention.** The standalone host's catalogue has 98 tool type rows: 64 Identified, 2 Specified, 3 Work-in-progress, 21 Prototype, 8 Implemented. Exactly one designer exists, in state Prototype. — [source: `standalone:docs/tools.md`; `standalone:docs/architecture.md:66`] (confidence: high, cited)
- No compliance or legal factor was found. Volumes (how many levels and requirements one document is expected to hold) are not stated anywhere. — [NEEDS CLARIFICATION: see Gaps]

## Evidence Against the Idea

- **The demand is one person's stated want.** No issue, no request from another user, no measurement of what the present way costs. The maintainer both raises the idea and is its only known user. — [source: intake; issue searches above] (confidence: high, cited)
- **The reported pain may be volume, not presentation.** Böckeler's complaint is that agent-written specs are verbose and repetitive, and that small problems drown in them ("like using a sledgehammer to crack a nut"). A form-based view of the same content shows the same amount of content. Whether a hierarchy and filters make it easier to judge is untested. — [source: martinfowler.com article; the inference is an ASSUMPTION] (confidence: medium)
- **Agents do not reliably keep to a format they are told to keep.** "I frequently saw the agent ultimately not follow all the instructions." A file whose structure the designer enforces, written by agents as text, will be out of structure some of the time, and the intake's answer for that case is an error. How often is unknown. — [source: martinfowler.com article; the frequency is an ASSUMPTION] (confidence: medium)
- **Answered by the change of 2026-10-13: a place-shaped requirement number as identity.** As first captured, `REQ-x.y.z` would have changed whenever a requirement or anything above it was moved, added before or deleted, and with it every link and assessment naming it; the organization's own Markdown tool records this as "a known limit" and the OMG issue names it as poor practice. `REQ-000x`, never changing, removes that objection, and gives the standalone host what its two-writer handling asks for, an edit that can "find what it edits by identity rather than by position". It is kept here so the later stages see why the identifier has this shape. — [source: `definitions/diagrams/agent-behavior-modelling.md` line 59; issues.omg.org SYSML17-142; `standalone:src/backend/EtAlii.Adp.Documents/WritableDocumentLifecycle.cs:193-197`; intake] (confidence: high, cited)
- **A counted number that never changes needs one party that gives it out, and the file has two writers.** The designer can count up; an agent or a user who adds a requirement as text has to pick a number without it, and two of them working from the same file state pick the same one. DESL's existing rules for that case (a duplicate id is reported, the first in reading order keeps it, and "A runtime **MUST NOT** change an id to resolve a duplicate, except by a user's action"; an element without an id is given one with the next edit) were written for UUIDs, where a clash is an accident and not the expected result of counting. A deleted requirement's number given out again would make an old link point at another requirement. — [source: `specifications/desl/DESL-specification.md` section 5.3.4; `specifications/fbl/FBL-specification.md` section 1.5; how often agents clash is an ASSUMPTION] (confidence: medium)
- **Prefixes written into the file are read by the agent too**, which the one existing Markdown tool avoided on purpose. `ITEM-0007` and `REQ-0042` on every bullet are tokens the agent must reproduce exactly and may invent, and the two look alike. With the place gone from the number, the number also no longer tells a reader where a requirement belongs. — [source: `definitions/diagrams/agent-behavior-modelling.md` line 59] (confidence: medium, cited; the effect on agents is an ASSUMPTION)
- **The tag list in the `.adp` file goes against two precedents.** The Knowledge designer keeps its options and colours in the document and requires that the designer "work the same after the registration is deleted and created again"; Agent Behavior Modelling states "Deleting it loses a layout, never a behavior." With the list in the `.adp` file, an agent that adds a tag as text cannot see or extend the list, and a lost `.adp` file loses the colours and the order. — [source: `standalone:.spec-workflow/specs/knowledge-designer/requirements.md:~158`; `definitions/diagrams/agent-behavior-modelling.md` line 12] (confidence: high, cited)
- **One tool would change four specifications.** A Markdown envelope in DED, a second surface kind and a counting id in DESL, a Markdown reading in FBL (plugin or family) and a new block in the registration, each with document, schema and examples, for a first user who is the tool engineer. The designer kind it builds on has one member, itself a Prototype. — [source: Data & Constraints above] (confidence: high, cited)
- **It would be a format no existing agent workflow reads.** Spec Kit, OpenSpec and Kiro each prescribe their own Markdown; the organization uses two of the kind already. A third format of the designer's own adds a file to keep in step with them unless it replaces or reads them, which the intake leaves open. — [source: github.com/github/spec-kit, github.com/Fission-AI/OpenSpec, kiro.dev; intake, First-Glance Unknowns] (confidence: medium, cited)
- **Structured requirement tools have small followings beside free-form ones.** Doorstop 680, StrictDoc 412 and rmToo 232 stars, against 141k and 71.7k for the tools that ask for plain Markdown with little structure. Star counts are a poor measure and the audiences differ (regulated engineering against agent coding), so this is a weak signal. — [source: the repositories above] (confidence: low, cited)
- **The largest nested-bullet Markdown tool is adding a database store.** Logseq's move suggests that Markdown files as the only store strain at some point; the reason is not on the page read. — [source: github.com/logseq/logseq; the reading is an ASSUMPTION] (confidence: low)
