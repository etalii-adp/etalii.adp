# Idea Research: One host-agnostic language for a whole tool

- **Slug**: host-agnostic-tool-language
- **Created**: 2026-10-14
- **Evidence confidence (overall)**: medium

This research is about the idea as the intake leaves it: shape 3. A tool type is a few Rust files, metadata included, compiled to one WebAssembly binary. That binary replaces the `.dis`, `.des` and `.fbl` files a tool engineer writes today, and it is run by every host. It replaces the current way of writing tool types once it is stable. The three notes written on 2026-10-13 under `notes/` already cover the prior art for shapes 1, 2 and 4: declarative viewpoint specifications, language workbenches, diagram language servers, grammars of graphics, lenses and the critiques. They are not repeated here. This document adds what bears on shape 3 in particular: who would write Rust, whether the WebAssembly runtimes each host needs are ready, how ecosystems built on WebAssembly and Rust have fared, and what the repositories themselves record.

What the repositories say is well evidenced. It was read from `origin/develop` of every clone, because most local working trees are behind (etalii.adp at `9063179`). How ready the runtimes are is evidenced by front pages, and some of it only by search summaries. The demand is the weakest part: the community of tool engineers the idea is for does not exist yet, and the maintainer calls it a guess.

Paths without a repository are in `etalii.adp`. `standalone:`, `intellij:`, `vscode:` and `notion:` mark paths in `etalii.adp.ide.standalone`, `etalii.adp.ide.intellij`, `etalii.adp.ide.vscode` and `etalii.adp.ide.notion`, all on `origin/develop` as of 2026-10-14.

## Users & Demand

- **The tool engineers the idea is for are hypothetical.** The intake gives the audience as a community of "enthusiasts" who would produce and consume tool types, "if we can create sufficient gravity towards the ADP concept". The maintainer calls this a guess. — [source: `intake.md`, *Clarifications*, first answer] (confidence: high, cited)
- **There is no outside participation today.** The 8 repositories of the organization have 1 star each (`.github` has 0), 0 forks, and discussions turned off. Of their 45 issues, 43 were opened by the maintainer and 2 by the site's refresh bot. No identity in any repository's history belongs to someone other than the maintainer, apart from agents and bots. — [source: `gh repo list etalii-adp --json name,stargazerCount,forkCount`; `gh search issues --owner etalii-adp`; `git shortlog -sn --all` per repository, 2026-10-14] (confidence: high, cited)
- **Nobody has asked for Rust or WebAssembly.** Searching the organization's issues for "rust", "wasm" and "webassembly" returns nothing. The "plugin" and "share" hits match the words inside issues about gaps between hosts, and none of them is about plugins or sharing as such. — [source: `gh search issues --owner etalii-adp`, 2026-10-14] (confidence: high, cited)
- **Observed behaviour: an AI assistant already writes the tool types, directed by the maintainer.** In etalii.adp, all 81 non-merge commits under `definitions/` carry `Co-Authored-By: Claude`, and 77 of them are authored by agent identities. Under `specifications/`, 51 of 53 are co-authored. So the de facto tool engineer today is an assistant, not a person writing by hand. The intake's question named this group, and the answer did not choose it. — [source: `git log origin/develop -- definitions/ specifications/`, 2026-10-14] (confidence: high, cited)
- **Observed behaviour: the hosts disagree, and this is the pain the idea addresses.** 13 open issues record one host deciding something differently from another, or something a second host "could not decide from the definition" (for example #64, #83, #96, #97, #98, #148, #152, #159, #162, #165). — [source: `gh issue list -R etalii-adp/etalii.adp`, 2026-10-14] (confidence: high, cited)
- **Observed behaviour: the same semantics are implemented several times, and the copies drift.** FBL exists three times: 8,717 lines in C# (standalone), 9,962 in TypeScript (VS Code) and 13,809 in Java (IntelliJ), 32,488 lines in all. The Notion add-on carries a fourth, byte-for-byte copy of VS Code's (8,835 lines). DISL is interpreted three times: 6,361 lines of C#, plus 3,007 in standalone's client, 6,319 lines in VS Code and 4,967 in Notion. CEL is implemented in C# (1,870 lines) and twice as a subset inside the FBL libraries, and DISL uses `@marcbachmann/cel-js`. — [source: line counts of `standalone:src/backend/EtAlii.Adp.Specification.{Disl,Fbl,Cel}`, `vscode:src/core/{disl,desl,fbl}`, `notion:src/{disl,fbl}`, `intellij:fbl/src/main`; `vscode:src/core/disl/ORIGIN.md:3`] (confidence: high, cited)
- **Observed behaviour: plugins are implemented unevenly, mostly nowhere.** The 29 `.dis` files declare 36 plugin ids. No host code names 27 of them, because standalone keeps that behaviour inside hand-written C# modules. VS Code registers 6 plugins, and Notion and IntelliJ register none. — [source: plugin blocks of `definitions/**/*.dis`; `vscode:src/core/plugins/index.ts:14`; `git grep` of every host for each id, 2026-10-14] (confidence: high, cited)
- **How many developers could write Rust, beside the alternatives.** In the 2025 Stack Overflow survey, 14.8% of all respondents (14.5% of professional developers) used Rust, against 66% for JavaScript, 43.6% for TypeScript, 29.4% for Java and 27.8% for C#. — [source: survey.stackoverflow.co/2025/technology] (confidence: high, cited) Rust was again the most admired language, at 72%. — [UNVERIFIED — search summary only, same site] (confidence: medium)
- **Rust is perceived as hard.** In the 2024 State of Rust survey (7,310 complete responses), "Around 31%" of non-users gave "the perception of difficulty as the primary reason for not using Rust". "53% consider themselves productive using Rust — up from 47% in 2023". Slow compilation was "at the top of the list" of what limits productivity, and "one of the top answers remained the worry that Rust will become too complex". — [source: blog.rust-lang.org, 2025-02-13] (confidence: high, cited; Rust users and the people around them, not ADP's audience)
- That an AI assistant writes Rust well enough for compiler feedback to beat JSON Schema validation as the first check, as `notes/rust-as-the-tool-language.md` §4 says, is not measured anywhere. — [ASSUMPTION] (confidence: low)

## Prior Art

### In this organization

- **WebAssembly was weighed three times before, and turned down each time.** Spec 006 rejected ".NET as WebAssembly" for the VS Code plug-in. Spec 009 rejected "Compiling standalone's C# for Node (WebAssembly)": "the plug-in must be one self-contained file of modest size and the repository has no .NET toolchain". Standalone chose "React + TypeScript client over Blazor WebAssembly", to be revisited "only if a specific chunk of C# logic clearly needs to run client-side". Each decision was about porting an existing host's code, not about a tool format. — [source: `specs/006-vscode-plugin/.spec-context.json:125`; `specs/009-vscode-fbl-implementation/research.md:24`; `standalone:.spec-workflow/steering/tech.md:145`] (confidence: high, cited)
- **No repository contains Rust, WebAssembly or an embedded JavaScript engine.** There is no `.rs`, `Cargo.toml` or `.wasm` file, and none of wasmtime, extism, chicory, GraalWasm, wasm-bindgen or wasmer appears. The only WebAssembly is pulled in by dev tooling (`wrangler`, `astro`, Pagefind). — [source: `git ls-tree -r` and `git grep` on all 8 repositories, 2026-10-14] (confidence: high, cited)
- **The specifications already plan for code and confine it.** DISL §1.2: "A conforming runtime needs no language-specific code … Whatever the declarative core cannot express is delegated to named, versioned plugins (section 13) rather than to embedded scripts." §1.4: "The common 90 % of diagram types must be expressible without code." FBL §1.4: "Declare what can be declared; contract the rest." FBL §11.5 names six formats "expected to stay plugins" (Turtle and N-Triples, SPARQL 1.1, `.sln`/`.slnx`/MSBuild, Ansible folders, Helm chart folders, Azure Pipelines template expansion). — [source: `specifications/disl/DISL-specification.md:95, :118`; `specifications/fbl/FBL-specification.md:110, :848-857`] (confidence: high, cited)
- **The declarative path has one existence proof.** The Notion add-on runs the Gartner hype cycle entirely from its `.dis` and `.fbl` files, and a test fails if any file under `src/` "names what only a tool type has". — [source: `notion:test/words.test.ts:7-8, :146-158`] (confidence: high, cited)
- **The declarative share can be raised without changing the format.** Spec 023 measured standalone's 16 module canvases at 9% declarative, 7% event handlers and 59% imperative code. After its tasks it measured 26%, 8% and 39%, at the cost of "nineteen central extensions". — [source: `specs/023-standalone-declarative-diagram-modules/standalone-declarative-diagram-modules.spec.md:45, :327`] (confidence: high, cited)
- **Tool types already travel between repositories as files, with provenance.** Hosts copy definitions byte for byte, with a `PROVENANCE.md` recording repository, path, commit and SHA-256, and check the copy in CI. Today most bindings live in standalone (20 `.fbl` files), against 2 in etalii.adp. — [source: `notion:addons/gartner-hype-cycle-graph/PROVENANCE.md:3-11`; `vscode:definitions/mindmap/PROVENANCE.md:5-11`; `git ls-tree` of both repositories] (confidence: high, cited)
- **The follow-on idea [tool-marketplace](../tool-marketplace/intake.md) depends on this one**, and so far it records only open questions. — [source: `.specify/assessments/tool-marketplace/intake.md`] (confidence: high, cited)

### WebAssembly plugin ecosystems written in Rust

- **Zed.** "Procedural parts of extensions are written in Rust and compiled to WebAssembly", target `wasm32-wasip2`. Extensions provide languages, debuggers, themes, icon themes, snippets and MCP servers. The docs list no kind of extension that changes Zed's interface. Most extensions "work without any Rust code": only language servers, context servers and debuggers need it. Published extensions must meet prerequisites. — [source: zed.dev/docs/extensions/developing-extensions] (confidence: high, cited) In the registry, "every submission is reviewed, and not all of them make the cut". — [source: github.com/zed-industries/extensions] (confidence: high, cited) Zed's reasons for WebAssembly: "cross-platform, and it's designed for running untrusted code safely", and "We wanted to make it impossible for an extension to crash Zed". Because "it would be very expensive to copy the syntax tree out of the wasm memory", only lexing runs in wasm. — [source: zed.dev/blog/language-extensions-part-1, 2024-04-18] (confidence: high, cited) Its Rust API is generated from WIT and versioned per Zed release. — [UNVERIFIED — search summary only] (confidence: medium)
- **Typst.** "Plugin functions must be pure", and this is not enforced. Plugins "run in isolation from your system", must be a "32-bit shared WebAssembly library" (WASI output does not load without stubbing), and exchange byte buffers. They are usually shipped inside packages with wrapper functions. — [source: typst.app/docs/reference/foundations/plugin] (confidence: high, cited) Forum users warn of "immense overhead in implementation" and costly data transfer. — [UNVERIFIED — search summary only] (confidence: low)
- **dprint.** Formatter plugins run as sandboxed WebAssembly "without access to the network or file system" and are loaded from a URL or a file path. — [UNVERIFIED — search summary only; dprint.dev not fetched] (confidence: medium)
- **Proxy-Wasm.** This is the closest precedent for one binary run by many hosts: an ABI that lets "consumers … use the same Proxy-Wasm extensions across different proxies", with hosts in ATS, Envoy, NGINX, MOSN and OpenResty and host libraries in C++, Go and Java. v0.2.1 is "the latest and widely implemented version". — [source: github.com/proxy-wasm/spec] (confidence: high, cited) Kong's NGINX module calls the ABI "still evolving" and points to each SDK's source as the reliable reference. — [UNVERIFIED — search summary only] (confidence: medium) Its scope is request filtering, with no user interface.
- **Helix** has no WebAssembly plugin system. Its candidate is an embedded Scheme (Steel) in a draft PR, and one commenter calls WebAssembly immature for plugins because the Component Model's ABI is not ready. — [UNVERIFIED — search summary only] (confidence: low)
- **Tree-sitter.** One grammar's source serves Zed, Neovim and Helix, but each editor builds or loads it differently. Zed loads wasm, while Neovim and Helix compile native libraries. — [UNVERIFIED — search summary only, apart from Zed's blog above] (confidence: medium)

### Describing interfaces in Rust

- **Slint keeps its interfaces out of Rust.** "Write your UI once in `.slint`, a simple markup language"; "Use a declarative language to separate your UI from business logic"; "Designers can work in parallel with developers". Its tooling (completion, live preview, a viewer with `--auto-reload`) is built on the `.slint` files. — [source: github.com/slint-ui/slint] (confidence: high, cited)
- **DSLs built from procedural macros are hard on the IDE.** According to a rust-analyzer developer, when a syntax error is introduced the macro panics or emits only `compile_error!`, and rust-analyzer then discards the item, so completion breaks while the user types. Other reports mention recomputation on every keystroke and longer compile times. — [UNVERIFIED — search summary only: lukaswirth.dev, reddit threads, a conference abstract] (confidence: medium for the mechanism, low for its size)

### Communities sharing tool content as data

- **Excalidraw libraries** are shared as JSON library files: built in the app, submitted, "changes may be requested if the guidelines above are not followed", MIT-licensed, English only. — [source: github.com/excalidraw/excalidraw-libraries] (confidence: high, cited) A shared library format needs no compiled code to be shareable.

## Market & Context

- **What the project does today:** an interpreter per host, plugins per host, and in standalone hand-written modules (76,331 lines of non-test backend C# over 68 diagram folders, plus 14,104 lines of module clients). IntelliJ has no DISL runtime, and Eclipse has no code ("There is no plug-in code yet"). — [source: line counts in `standalone:src/diagrams/`; `intellij:fbl/src/main/java/etalii/adp/fbl/plugin/`; `etalii.adp.ide.eclipse/README.md:5`] (confidence: high, cited)
- **The cost of doing nothing** is what the evidence above shows: hosts that diverge (13 open issues), duplicated FBL (32,488 lines in three languages) and plugins that exist in one host only. Doing nothing does not stop the work. Spec 023 and the per-host interpreters continue it. — [source: as above] (confidence: high, cited) Nothing measures how long a decision that diverges takes to settle, or how often a tool behaves differently between hosts in use. — [ASSUMPTION] (confidence: low)
- **Shape 3 is not the only way to stop hosts from diverging.** The notes describe two others: a shared logic runtime (shape 4, "turn five interpreters into one") and shared fixtures run in every host's CI, of which FBL's round-trip fixtures are a start. — [source: `notes/rust-as-the-tool-language.md` §7; `notes/one-declarative-tool-language.md` §8; `specifications/fbl/FBL-specification.md` §15.3] (confidence: high, cited)
- **Where the hosts render:**
  - IntelliJ draws with Swing and Java2D (`DiagramCanvas extends JComponent`), and JCEF is used nowhere. — [source: `intellij:core/src/main/java/etalii/adp/core/diagram/view/DiagramCanvas.java:53, :290`] (confidence: high, cited)
  - VS Code runs tool logic in the extension host, and its webviews only draw: "a webview draws what it is sent and computes nothing of a tool type". — [source: `vscode:CLAUDE.md:20`; `vscode:src/extension/toolEditor.ts:424-428`] (confidence: high, cited)
  - The Notion add-on is a static page shown in an embed block, built by esbuild for the browser and published on GitHub Pages. No Content-Security-Policy is set. — [source: `notion:addons/gartner-hype-cycle-graph/index.html:1-12`; `notion:scripts/build.mjs:85-89`; grep of the Notion and site repositories] (confidence: high, cited)
  - Standalone is a .NET 10 backend with a React client in a browser. Modules are compiled in through glob project references and found by reflection, not loaded from folders. — [source: `standalone:src/Directory.Build.props:19`; `standalone:src/backend/EtAlii.Adp.Backend.Service/EtAlii.Adp.Backend.Service.csproj:17-19, :30-31`] (confidence: high, cited)
  - So the hosts that would run the binary are Node (VS Code), a browser (Notion, standalone's client), .NET (standalone's backend) and the JVM (IntelliJ, Eclipse).
- Browsers and Node run core WebAssembly modules without anything added, so Notion and VS Code would need no runtime dependency for the binary itself. — [ASSUMPTION; generally known, not checked against these hosts] (confidence: high)

## Data & Constraints

### WebAssembly runtimes per host

- **JVM (IntelliJ, Eclipse).**
  - Chicory is a "Native JVM WebAssembly runtime" with "zero native dependencies or JNI". Being "the fastest runtime" is a stated non-goal, and the roadmap lists "Compiler out of experimental" and, for 2026, "Performance". Its users include Bazel, Trino, Debezium, JRuby and Apache Camel. The Component Model is not mentioned. — [source: github.com/dylibso/chicory] (confidence: high, cited) It reached 1.0.0, and later releases (1.6.0) followed. — [UNVERIFIED — search summary only] (confidence: medium)
  - Extism, the JSON-in, JSON-out convention the notes assume, has two Java SDKs. The main SDK needs a native library ("you first need to install the Extism Runtime", `libextism`). The pure-Java SDK on Chicory is "an experimental Java SDK", "still very experimental", at version `999-SNAPSHOT`. The note's sketch of "Extism's Java SDK on Chicory, pure Java, no native library" therefore describes an experimental SDK, not the supported one. — [source: github.com/extism/java-sdk; github.com/extism/chicory-sdk; `notes/mindmap-capabilities-example.md` §6] (confidence: high, cited)
  - GraalWasm is "fully supported" under Oracle GraalVM, pure Java, with WebAssembly 2.0. Whether it runs inside the IntelliJ Platform's JetBrains Runtime was not looked at. — [UNVERIFIED — search summary only] (confidence: low)
- **.NET (standalone's backend).** wasmtime-dotnet is a Bytecode Alliance project whose GitHub page shows no releases, says nothing about the Component Model, and builds against a downloaded Wasmtime for each platform, which means a native library. A NuGet aggregator lists version 44.0.0 of May 2026. — [source: github.com/bytecodealliance/wasmtime-dotnet; the version is UNVERIFIED — search summary only] (confidence: medium)
- **The Component Model, the typed-interface layer, is not available everywhere.** Browsers have no native support. `jco transpile` turns components into core wasm plus JavaScript, with browser support "experimental, and not currently suitable for production". No runtime above mentions it for the JVM. — [UNVERIFIED — search summary only] (confidence: medium) A tool binary every host can load is then a core module with an ABI of the project's own, the way Typst and Extism each define one. Zed uses `wasm32-wasip2`, Typst a non-WASI 32-bit library, and Extism its own convention. — [source: the Zed, Typst and Extism pages above] (confidence: high, cited)
- **Rust's own users use WebAssembly mostly in the browser** (23%, against 7% for other uses). — [source: blog.rust-lang.org, 2024 survey results] (confidence: high, cited)

### What the project's rules say

- **The constitution assumes a document others implement.** Principle II, "Implementable from the Document Alone": "a normative document from which an implementer can build a conforming validator, generator or runtime; a machine-readable schema …; worked examples". "Schemas are JSON Schema, draft 2020-12". Its readers are "the developers of the ADP hosts, who implement the specifications", and "implementers in four languages need to read the same obligation the same way". Shape 3 makes a Rust library what a tool type is written against. It conflicts with principle II unless a normative contract stays beside the library (the note's extracted `describe()` JSON). — [source: `.specify/memory/constitution.md:10, :20-26, :35, :39`; `notes/rust-as-the-tool-language.md` §3] (confidence: high for the text, cited; the conflict is an interpretation)
- **Principle V:** "A construct, format or dependency MUST be justified by a current tool's need, not an anticipated one." The case for shape 3 rests on an ecosystem that is anticipated, not current. — [source: `.specify/memory/constitution.md:49`; intake] (confidence: high, cited)
- **Code from others needs a trust decision.** DISL §13: "Runtimes MUST NOT download and execute code automatically without user or administrator approval." §16: "Plugins are code and MUST be installed through an explicit trust decision." Under shape 3, every tool type is code. — [source: `specifications/disl/DISL-specification.md:4709, :4856`] (confidence: high, cited)
- **What the host principles say about dependencies:**
  - IntelliJ: third-party dependencies "MUST be Apache-2.0-compatible and SHOULD be ones the IntelliJ Platform already bundles", the plug-in uses "the platform's own mechanism wherever the platform provides one", and "No network access at runtime is required or performed by any tool". — [source: `.specify/memory/repositories/etalii.adp.ide.intellij.md:11-14, :74-76, :92-94`] (confidence: high, cited)
  - VS Code: dependencies "MUST be justified by a current requirement", the plug-in performs no network access at run time, and "Every webview MUST carry a content security policy that allows only the plug-in's own scripts and styles". The CSP allows no `wasm-unsafe-eval`, which matters only if a binary were run in a webview rather than in the extension host. — [source: `.specify/memory/repositories/etalii.adp.ide.vscode.md:61, :68, :71`; `vscode:src/extension/webviewHtml.ts:18-24`] (confidence: high, cited)
  - Notion: published "by GitHub Pages only", and "A … build step or a hosting service MUST be justified by a current requirement". — [source: `.specify/memory/repositories/etalii.adp.ide.notion.md:48, :54-57`] (confidence: high, cited)
  - Under these rules a WebAssembly runtime in IntelliJ is a new dependency that the platform does not bundle. — [interpretation of the rules above] (confidence: medium)
- **Toolchains today:** .NET 10 SDK `10.0.203` (standalone), Java 25 with 0 Kotlin files (IntelliJ), Node 24 and esbuild (VS Code, Notion). There is no Rust toolchain in any repository or workflow. — [source: `standalone:src/global.json`; `intellij:gradle.properties`; `notion:package.json:9`] (confidence: high, cited)
- **What would be migrated:** 29 `.dis` files, 1 `.des` file and 2 `.fbl` files with 33 companion documents in etalii.adp, 20 `.fbl` files in standalone, the four interpreters and three FBL libraries above, and the readers of `.dis` files outside the hosts (the example validator, the site's catalogue, the Notion "Tools" database). — [source: `git ls-tree -r origin/develop definitions`; `notes/rust-as-the-tool-language.md` §3; CLAUDE.md, *Writing specifications*] (confidence: high, cited)
- **Package size today:** a local build of the VS Code plug-in is 1,159,151 bytes (`dist/extension.js` 428,589), and the IntelliJ plug-in is 533,800 bytes. The note estimates "perhaps 1–3 MB per tool" for a binary that carries the runtime. — [source: stale local build outputs, `intellij:build/distributions/etalii-adp-0.1.0.zip` (28 September) and `vscode:etalii-adp-0.1.0.vsix` (5 October); `notes/rust-as-the-tool-language.md` §5] (confidence: medium for the sizes; the estimate is an ASSUMPTION, low)
- **Supply chain.** In 2025 and early 2026, extension marketplaces of the kind the follow-on idea imagines had repeated incidents: an Open VSX flaw that could have pushed updates to every extension, more than 550 secrets leaked across 500 extensions, the GlassWorm campaign through established extensions, and a $500,000 theft through a fake Solidity extension. — [UNVERIFIED — search summary only: thehackernews.com and vendor blogs] (confidence: medium)

## Evidence Against the Idea

- **The ecosystem that justifies it does not exist, and nothing suggests it is near.** The case for replacing the current way completely is sharing within a community of tool engineers. Today there are no outside contributors, no forks and no issue from anyone but the maintainer, and the maintainer calls the community a guess. Principle V asks for a current need. — [source: Users & Demand above; `.specify/memory/constitution.md:49`] (confidence: high, cited)
- **Rust narrows who can write a tool type.** About one developer in seven uses Rust, against two in three for JavaScript and more than two in five for TypeScript. About 31% of non-users stay away because Rust looks difficult, and slow compilation tops its users' complaints. A community of "enthusiasts … technically skilled enough" is smaller in Rust than in a data format or TypeScript. — [source: survey.stackoverflow.co 2025; blog.rust-lang.org 2024 results] (confidence: medium, cited; ADP's possible audience was not surveyed)
- **Ecosystems built on Rust and WebAssembly still keep the common part as data.** In Zed, the most direct precedent, most extensions "work without any Rust code", and Rust is needed only where a process has to be started. Slint describes interfaces in its own markup, for tooling and for people who do not program. Shape 3 puts even the metadata in Rust, which none of these does. — [source: zed.dev/docs/extensions/developing-extensions; github.com/slint-ui/slint] (confidence: high, cited)
- **The binary ecosystems found do not extend the user interface.** Zed lists no kind of extension that changes the interface. Typst plugins are pure functions, and Proxy-Wasm filters requests. A whole tool (canvas, gestures, forms) loaded as WebAssembly into several native hosts has no precedent among the systems found. The nearest, GLSP in the notes, has a server written in code and a client in a browser, not native views. — [source: the pages above; `notes/one-declarative-tool-language.md` §3.3] (confidence: medium, cited; the search was not exhaustive)
- **On the JVM the runtime is not ready in the form the sketch assumes.** Extism's pure-Java SDK is experimental, and the supported one needs a native library. Chicory gives up speed by design and still calls its compiler experimental. The Component Model is not available in any of these runtimes. IntelliJ's principles prefer dependencies the platform already bundles. — [source: Data & Constraints above] (confidence: medium, cited)
- **The project has said no to WebAssembly three times**, each time for size and toolchain reasons ("one self-contained file of modest size", "the repository has no .NET toolchain"). Shape 3 adds a Rust toolchain that no repository has. — [source: `specs/009-vscode-fbl-implementation/research.md:24`; `specs/006-vscode-plugin/.spec-context.json:125`; `standalone:.spec-workflow/steering/tech.md:145`] (confidence: high, cited; those decisions were about porting host code, not about a tool format)
- **"Rust tool types can be shared" applies equally to today's files.** Specification files are already files that move between repositories with their provenance, and Excalidraw's community shares JSON libraries behind a review. What sharing Rust adds is code from strangers, which DISL §16 puts behind a trust decision and which extension marketplaces have repeatedly seen abused. — [source: provenance files above; github.com/excalidraw/excalidraw-libraries; `specifications/disl/DISL-specification.md:4856`; the incidents are a search summary] (confidence: medium, cited)
- **It turns the specification into an implementation.** The constitution is written for hosts that implement the documents in four languages. A Rust library that a tool type is written against becomes the standard, and a tool type in Rust is no longer data that the validator, the site catalogue, the Notion "Tools" database or an assistant can read without running it. The note keeps an extracted JSON description for this reason, which means a contract much like today's DISL still has to be specified and maintained. — [source: `.specify/memory/constitution.md:10, :20-26`; `notes/rust-as-the-tool-language.md` §3, §5] (confidence: high, cited)
- **Interfaces written in Rust macros cost IDE support and edit-to-preview time.** rust-analyzer drops a macro item while it has a syntax error, and a change to a tool type needs a rebuild, where a JSON edit shows at once in VS Code and standalone today. — [UNVERIFIED for the rust-analyzer behaviour — search summary only; `notes/rust-as-the-tool-language.md` §5 for the rebuild] (confidence: medium)
- **Crossing the WebAssembly boundary is not free.** Zed runs only lexing in wasm because copying a syntax tree out of wasm memory "would be very expensive", and Typst users warn about the cost of transfer. Shape 3 puts the scene a host draws behind that boundary on every transaction. — [source: zed.dev/blog/language-extensions-part-1; Typst forum (search summary)] (confidence: medium)
- **The problem can be reduced in smaller steps.** Host divergence and duplicated semantics are what the evidence shows to hurt. A shared runtime with declarative tool types (shape 4) or shared fixtures address them without moving every tool type into code, and spec 023 shows the declarative share rising (9% to 26%) within today's format. — [source: `notes/rust-as-the-tool-language.md` §7; `specs/023-standalone-declarative-diagram-modules/…spec.md:327`] (confidence: medium, cited)
- **The migration is large and lands during other work.** It touches 30 tool types, four interpreters, three FBL libraries, 76k lines of standalone module code and the validators. The maintainer has already said it must wait for an explicit go because it is "too disruptive". — [source: Data & Constraints above; intake, *Clarifications*] (confidence: high, cited)
