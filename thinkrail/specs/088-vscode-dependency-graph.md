# Feature Specification: The Dependency Graph in VS Code, as the Standalone One

**Feature Branch**: `features/088-vscode-dependency-graph`

**Created**: 2026-11-23

**Status**: Implemented on 2026-11-23, in etalii.adp.ide.vscode #82, #83 and #85, with the definition's changes in etalii.adp (#787 to #813) and standalone's re-bundles (approved 2026-11-23, Peter, decision card "Approve, then build")

**Input**: Peter, 2026-11-23, asked for a thread that brings a tool of the standalone host ("the standard host") to the VS Code host, functionally identical to it; his words named the tool by a phrase that is no tool type's name, so on a decision card the same day he chose the dependency graph. The work follows the causal loop diagram's ([spec 081](../../specs/081-vscode-causal-loop-diagram/vscode-causal-loop-diagram.spec.md)): an inventory of the differences, each traced to a requirement, confirmed before anything is built.

## Context

The dependency graph (`generic/dependencies`, extension `.dgr`) is defined in `definitions/diagrams/dependency-graph.dis` and its companion `dependency-graph.md`, with the binding `dependency-graph.fbl` in `etalii.adp.ide.standalone`. The standalone host draws it from that definition, with the code the companion lists under *What remains in the module, and why*, and holds itself to the parity transcript `dependency-graph.transcript.json`: what its module answers for 39 documents (13 files and 26 inline cases), with 1,202 recorded edits. The VS Code host (`etalii.adp.ide.vscode`) builds every tool type from its definition and has no dependency graph: none of its `definitions/` folders is this tool type.

The inventory (2026-11-23; standalone `develop` at `0047236`, VS Code `develop` at `3c17376`, etalii.adp `develop` at `673e4fc`) copied the definition into VS Code on a scratch branch, opened every document of the transcript through VS Code's own interpreter, and replayed the transcript's menus, property rows, findings and edits. The definition reads: a `.dgr` opens, a new one is made from the binding's template, the toolbox, the menus of a node, a dependency and the empty canvas, and the rows of ADP Properties come out as the standalone host gives them, and 504 of the 1,202 edits already write the transcript's bytes. The rest fall into the rows below. Requests the transcript records that no canvas, menu or row of VS Code can make (an action on an id the document does not hold, a node's operation on a dependency, a made-up action id) are not differences; they are listed in VS Code's parity test with the reason, as spec 081 did.

### What this feature is not

- **Not a change to the standalone host.** It is the reference; nothing there changes, apart from taking a newer copy of the definition if FR-008 changes it.
- **Not a change to what a `.dgr` file holds.** Every gesture writes what the standalone host writes for it, byte for byte.
- **Not a host for one tool type.** What VS Code lacks of DISL here (an edge's `connect.from`, a library tool's `createSource` and `createTarget`, a form value checked as text) is built for every diagram it reads. What only this tool type needs is a plugin its definition names (`net.etalii.adp.generic.dependencyCurve`, `net.etalii.adp.generic.dependencyEnds`) or a row under "Code for one tool type" in VS Code's `docs/disl-support.md`, with its reason.
- **Not new behaviour.** Cycle detection, reconnecting a dependency's end, copy and paste, multi-select and automatic layout are absent from the standalone host and stay absent here.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Open a dependency graph and read it (Priority: P1)

A person opens `services.dgr` in VS Code and sees what the standalone host shows: ten services as boxes on their rows, each dependency a curve from the dependent's right side to the left side of what it depends on, looping forward where the dependency sits behind, with its label above the middle and a filled arrowhead at the dependency.

**Why this priority**: Nothing else is of use until a file opens and draws.

**Independent Test**: `services.dgr` opened in both hosts, in the light and the dark theme, and the screenshots compared part by part against rows A1 – A3 and B1 – B5.

**Acceptance Scenarios**:

1. **Given** `services.dgr`, **When** it opens in VS Code, **Then** every node stands at its `x` and on its row, every dependency is drawn, and the Problems panel shows no finding.
2. **Given** a dependency whose dependency lies left of its dependent, **When** it is drawn, **Then** the curve leaves the dependent's right side and loops forward into the dependency's left side.
3. **Given** the dark theme, **When** the graph is drawn, **Then** the boxes, their borders, their text and the lines use the standalone host's dark colours.
4. **Given** a file that writes its `relations:` above its `elements:`, **When** it opens, **Then** each dependency is joined to its nodes as in the standalone host.

---

### User Story 2 - Build a graph with the toolbox, the anchors and the keys (Priority: P1)

A person drops a Node on the canvas and gets "New node" on the row nearest the drop; drags from its right anchor onto another node to make it depend on that node, from its left anchor to make the other depend on it, or onto empty canvas to create the other node there in the same step; and presses Tab and Enter on a selected node to add one to its right or below it.

**Why this priority**: It is how a graph is made; a viewer alone is not the tool Peter has in the standalone host.

**Independent Test**: For every gesture of the standalone canvas, the same gesture in VS Code on the same file makes the same change to the file and one step of VS Code's undo.

**Acceptance Scenarios**:

1. **Given** a node, **When** a dependency is drawn from its left anchor to another node, **Then** the file gains a dependency whose `from` is the other node and whose `to` is the dragged one.
2. **Given** a node, **When** a dependency is dragged from its right anchor and released on empty canvas, **Then** a node labelled "New node" is added at the release point on the nearest row, with a dependency on it, and one undo removes both.
3. **Given** a node, **When** a dependency is drawn from it onto itself, **Then** nothing changes and "A node cannot depend on itself." is shown.
4. **Given** a selected node, **When** Tab is pressed, **Then** a node is added 240 to its right on the same row, which the selected node depends on.

---

### User Story 3 - See what is wrong with a graph (Priority: P2)

A person editing a `.dgr` by hand sees in the Problems panel the same findings the standalone host gives, in the same order: a node or dependency with no id, an id declared twice, a dependency that names no node, and a node that depends on itself.

**Why this priority**: The findings are how a hand-written file is kept honest; without the dangling ones a typo in an id goes unseen.

**Independent Test**: The findings of the 39 documents of the standalone transcript, compared with the transcript's.

**Acceptance Scenarios**:

1. **Given** the transcript's `inline/dangling-relation`, **When** it opens, **Then** the Problems panel lists one finding for each end that names no node, with the definition's sentence.
2. **Given** the transcript's `inline/every-rule-interleaved`, **Then** the findings come in the standalone host's order: the ids first, in declaration order with nodes before dependencies, then each dependency's dangling ends and its self-dependency.

---

### User Story 4 - Edit a node's place and label in ADP Properties (Priority: P2)

A person selects a node and types a new X, Row or Label in ADP Properties; selects a dependency and changes its Label, and sees its two ends as read-only rows with the reason.

**Why this priority**: The property rows are the precise way to place a node, and the standalone host offers them.

**Independent Test**: Each property edit of the transcript made in VS Code writes the same bytes, and each refused one is refused with the same sentence.

**Acceptance Scenarios**:

1. **Given** a node, **When** X is set to `1234.5`, **Then** the file's `x` becomes `1234.5`; **and when** Row is set to `1.5`, **Then** it is refused with "'1.5' is not a number this graph can place a node at."
2. **Given** a node whose `x` is `8.072929300833366`, **When** it is selected, **Then** ADP Properties shows X as `8.0729`, as the standalone host does.

### Edge Cases

- An empty file, or one whose root is not a mapping: it opens as an empty graph, and adding a node is refused with "The file has no place to create elements in."
- A file that is not YAML: it opens, the canvas says it is unavailable, the Problems panel has one error, and every edit is refused (FR-004).
- A node or dependency written as a one-line flow mapping, or a value reached through a merge key or an alias: kept, read as the standalone host reads it, and an edit to it refused with the binding's sentence (FR-016).
- Two dependencies between the same pair: drawn on the same curve.
- An id held twice: the first holder is the one every gesture edits.
- A file opened read-only: no toolbox, no anchors and no menu entries that edit.

## Requirements *(mandatory)*

### Functional Requirements

Each requirement names the inventory rows it closes. "As the standalone host does" means as the standalone module `src/diagrams/dependency-graph/` on `develop` at `0047236` does, which its parity transcript `dependency-graph.transcript.json` records.

**Opening and reading**

- **FR-001** (A1): A `.dgr` file **MUST** open in the dependency graph in VS Code with no finding that a feature of the definition is unsupported, and **New Dependency graph** **MUST** create the binding's template.
- **FR-002** (A2): VS Code's examples **MUST** include the standalone host's `services.dgr` with the files that come with it.
- **FR-003** (A3): Nodes **MUST** be read before dependencies whatever order the file writes them in, so that every gesture, row and finding sees the same graph as the standalone host.
- **FR-004** (A4): An edit of a file that does not read **MUST** be refused with the standalone host's sentence, naming the file.

**The drawing**

- **FR-005** (B1): A dependency **MUST** be drawn as the companion's dependency curve: a horizontal curve between the facing sides where the dependency lies to the right of its dependent, and a forward loop out of the dependent's right side into the dependency's left side otherwise.
- **FR-006** (B2): A dependency's ends **MUST** attach on the sides the standalone host attaches them to, and **MUST** follow a node while it is dragged.
- **FR-007** (B3): A dependency's label **MUST** be drawn above the middle of its line, in the standalone host's size.
- **FR-008** (B4): In the dark theme the boxes, borders, text and lines **MUST** take the standalone host's dark colours. Where the definition does not state them, they **MUST** be added to the definition in etalii.adp, as was done for the causal loop diagram, and VS Code **MUST** take the newer copy.
- **FR-009** (B5): The arrowhead **MUST** be a filled triangle at the dependency's end, in its line's colour.

**Gestures**

- **FR-010** (C1): A dependency drawn from a node's right anchor **MUST** make the dragged node depend on the one it lands on, and one drawn from its left anchor **MUST** make the landed-on node depend on the dragged one, as the edge's `connect.from` states.
- **FR-011** (C2): A dependency released on empty canvas **MUST** create a node labelled "New node" at the release point on the nearest row and the dependency, as one undo step: the new node is the dependency from the right anchor and the dependent from the left one, as the library tool's `createTarget` and `createSource` state.
- **FR-012** (C3): A dependency drawn from a node onto itself **MUST** be refused with "A node cannot depend on itself.", and one that lands on something that is not a node **MUST** be refused with "Both ends of a dependency must be nodes of this graph."
- **FR-013** (C4): Tab and Enter on a selected node **MUST** add a node 240 to its right on the same row, or at its `x` one row down, which the selected node depends on, as one undo step.
- **FR-014** (C5): Adding a node with no point to place it at, from the Command Palette, **MUST** ask for its label as the standalone host does ("Add node", field "Label", prefilled "New node", button "Add") and place it 240 right of the selected node, or at 0 on row 0 with nothing selected.
- **FR-015** (C6): Adding a node to an empty file, or to one whose root is not a mapping, **MUST** be refused with "The file has no place to create elements in."
- **FR-016** (C7): An edit of a value reached through a merge key or an alias **MUST** be refused with the binding's sentence before the value is checked.

**ADP Properties**

- **FR-017** (D1): A node's X **MUST** be shown with at most four decimals, as the standalone host shows it.
- **FR-018** (D2): X **MUST** accept every number the definition's pattern accepts (`1234.5`, `0.00001`, `1e21`) and write it in FBL's form, and Row **MUST** accept a whole number, negative ones included, and refuse any other value with the definition's sentence.
- **FR-019** (D3): X and Row **MUST** be edited in the control the standalone host offers for them, a line of text, and VS Code's parity record **MUST** say so where it differs from the definition's `number` widget.

**Findings**

- **FR-020** (E1): A node or dependency with no id **MUST** be reported by the definition's rule `missingId`, with its code and sentence, and not by DISL's built-in missing-id finding.
- **FR-021** (E2): A dependency end that names an id no node holds **MUST** be reported with the definition's dangling-relation sentence, once per end, reading the id as the file writes it.
- **FR-022** (E3): The findings **MUST** come in the standalone host's order: missing and duplicate ids first, in declaration order with nodes before dependencies, then for each dependency in declaration order its dangling `from`, its dangling `to` and its self-dependency.

**Throughout**

- **FR-023**: Every gesture **MUST** be one edit of the text document and one step of VS Code's undo, leaving every byte it does not concern as it was; a refused gesture **MUST** change nothing and show its reason.
- **FR-024**: What VS Code builds here of DISL **MUST** serve every diagram it reads and name no tool type; what only this tool type needs **MUST** be a plugin its definition names or a row under "Code for one tool type" in VS Code's `docs/disl-support.md`.
- **FR-025**: VS Code **MUST** hold its dependency graph to its own copy of the standalone transcript and the documents it records, in a test that runs in its build.
- **FR-026**: VS Code's `docs/tools.md`, `README.md`, `docs/disl-support.md` and `docs/parity.md` **MUST** describe the dependency graph as built, in the change that builds it, and a screenshot of it **MUST** be added.

### Key Entities

- **Node**: something other things can depend on, keyed by its id, with a label, an `x` and a row.
- **Dependency**: a claim that one node (`from`, the dependent) depends on another (`to`), with an optional label.
- **Transcript**: the standalone host's record of what its dependency graph answers for 39 documents: toolbox, menus, rows, findings, payloads and every edit's bytes.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Of the 22 inventory rows, 22 are closed: a side-by-side check of `services.dgr` in both hosts, in both themes, finds none of them again.
- **SC-002**: For each of the 39 documents of the standalone transcript, VS Code gives the same toolbox, menus, property rows and findings, and every edit of the transcript writes the same bytes, apart from what VS Code's parity record lists with its reason.
- **SC-003**: The definition reads in VS Code with no finding that a part of it is unsupported, and every expression in it evaluates.
- **SC-004**: A person new to the tool can go from **New Dependency graph** to three connected nodes in under two minutes with no error, no dead end and no step that needs the documentation; the host test records the attempt.
- **SC-005**: No part of VS Code's shared DISL support built for this feature names a tool type, an element type or an attribute of the dependency graph, as VS Code's existing word check holds.

## Assumptions

- The standalone host on `develop` at `0047236` and its transcript are the reference. Where the standalone host and the definition disagree, the standalone host's behaviour is followed; where the two only look different, the definition is changed to the standalone host's look, as Peter chose for the causal loop diagram on 2026-11-22. A difference this feature meets that the companion does not record is raised as an issue in etalii.adp. One is known already: section 4 of the companion says the X row shows the number as the file writes it, where the standalone host rounds it to four decimals (FR-017).
- The definition is read as it is in etalii.adp at `673e4fc`; a newer copy taken during the work is followed if it changes nothing this feature relies on.
- The wording of the error for a file that is not YAML comes from each host's YAML reader and may differ, as it does for the Gartner hype cycle graph; its code, its line and that it is an error are held.
- The work lands in `etalii.adp.ide.vscode` in a few pull requests: reading and findings, the drawing, gestures, properties, and the transcript test with the documents. Anything taken from the definition into etalii.adp (FR-008) lands there first. The side-by-side check and the screenshot are taken on the Mac mini.
