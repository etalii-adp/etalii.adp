## Context

**The problem.** Service level management, in ITIL's terms, agrees and monitors the levels of service a provider commits to. Reliability engineering expresses the same commitments as service level indicators (SLIs), service level objectives (SLOs) and error budgets, and increasingly writes them as code. OpenSLO is an open, vendor-neutral specification for that code: YAML documents in the shape of Kubernetes manifests, each with an `apiVersion` and a `kind` (Service, SLI, SLO, DataSource, AlertPolicy, AlertCondition, AlertNotificationTarget), published under the Apache License 2.0. Its tools parse, validate and convert; none shows the documents as what they describe. A service level manager who should review the commitments reads YAML, or does not read them at all, and the two worlds that describe one commitment stay apart.

**What this feature delivers.** The definition of a new diagram type, the **SLO map** (`openslo/slo`), in this repository: its specification, its FBL binding to OpenSLO documents, its tool description, its companion document, and fixtures taken from real published OpenSLO documents. The diagram opens OpenSLO files where they already are, in the repositories beside the code, and changes them with byte-preserving edits. Building it in a host is a separate feature per host and is not in scope.

**Words.** A **service** is what a set of objectives is about. An **SLI** is the measure (a ratio of good to total events, or a threshold on a metric). An **SLO** is a target for an SLI over a **time window**, with a **budgeting method**. The **error budget** is the share of the window the target allows to fail. An **alert policy** says when the budget's consumption is told to someone, through **alert conditions** and **notification targets**. A **data source** is where an SLI's metrics come from. These are OpenSLO's words; the rest are those of [docs/terminology.md](../../docs/terminology.md).

### What this feature is not

- It does not query metrics or show live budget consumption: it shows the commitments, not their current state.
- It does not define its own SLO format: the files are OpenSLO's, and a need OpenSLO cannot state is recorded, not invented.
- It does not cover service level agreements as contracts or experience level agreements; the research names the latter as a later extension.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Read a service's objectives as one picture (Priority: P1)

A service level manager opens the OpenSLO file of a payment service. They see the service, its SLOs, the SLI each one measures, the data source behind each SLI, and the alert policies with their conditions and targets, as one connected picture. Each SLO shows its target, its window and the error budget that follows, in words a non-engineer reads ("99.9 % of requests over 28 days; 40 minutes of failure allowed").

**Why this priority**: making the commitments readable to the people who agree them is the gap. With nothing else built, a review no longer needs a YAML reader.

**Independent Test**: open each fixture and compare every element and connection with the file's documents and references.

**Acceptance Scenarios**:

1. **Given** a file holding a Service, two SLOs, their SLIs and one AlertPolicy, **When** it is opened, **Then** each document is an element and each reference between them a connection.
2. **Given** an SLO with target 0.999 and a rolling window of 28 days, **When** it is shown, **Then** it states 99.9 %, 28 days rolling and an error budget of 40 minutes 19 seconds.
3. **Given** an SLO whose SLI is defined inline rather than by reference, **When** it is shown, **Then** the SLI is drawn as its own element joined to the SLO, marked as inline.
4. **Given** objectives spread over several files in one folder, **When** one is opened, **Then** references into the other files are drawn and the elements from other files are marked as such.

---

### User Story 2 - Edit an objective through a form (Priority: P1)

An engineer changes an SLO's target from 99.9 % to 99.95 % and its window from 28 to 30 days in a form, and adds a second objective to the service. Only those values change in the file; comments, ordering and formatting elsewhere stay as they were.

**Why this priority**: a diagram that cannot write leaves the review and the change in different places.

**Independent Test**: make each kind of edit in the diagram and compare the file byte for byte with the expected result.

**Acceptance Scenarios**:

1. **Given** an open file, **When** the user changes one SLO's target, **Then** only that value changes in the file and every other byte is what it was.
2. **Given** a service, **When** the user adds an SLO from the toolbox, **Then** a new OpenSLO SLO document is written with the service and an SLI referenced, and the file stays valid OpenSLO.
3. **Given** an SLI referenced by two SLOs, **When** the user deletes it, **Then** they are asked to confirm and told which SLOs refer to it.

---

### User Story 3 - See what is missing or inconsistent (Priority: P2)

The diagram reports what OpenSLO's own rules refuse and what a reviewer would question: an SLO without an alert policy, a reference to a document that does not exist, a target above 100 %, two objectives on one SLI with conflicting windows.

**Why this priority**: review is the reason the manager opens the file, and these are the questions a review asks.

**Independent Test**: open a fixture with one planted fault of each kind and check that each finding stands at the right element.

**Acceptance Scenarios**:

1. **Given** an SLO that names a missing SLI, **When** the file is opened, **Then** a finding stands at the SLO naming the missing reference.
2. **Given** an SLO with no alert policy, **When** the file is opened, **Then** an informative finding stands at it.
3. **Given** a document of a kind the diagram does not draw, **When** the file is opened, **Then** it is kept as written and listed, and nothing is lost when the file is written.

---

### User Story 4 - A person and an agent work on the same file (Priority: P2)

An agent writes or tunes objectives in the YAML, for example after an incident review. The person sees the change in the diagram without reopening, and the agent can write valid documents from the companion document alone.

**Why this priority**: SLO files are already written by engineers and increasingly by agents; the diagram is where a person checks what was written.

**Independent Test**: edit an open file as text in each way a fixture covers, and check the diagram after each.

**Acceptance Scenarios**:

1. **Given** an open file, **When** an agent changes a target in the text, **Then** the diagram shows the new value and budget without being reopened.
2. **Given** only the companion document, **When** an agent writes a Service with one SLO and one SLI, **Then** the diagram opens it without a finding and OpenSLO's own validator accepts it.

---

### User Story 5 - A host builds the diagram from its definition (Priority: P1)

A developer of a host builds the SLO map from the definition alone, and its fixtures are real published OpenSLO documents.

**Why this priority**: every host implements the one specification (constitution, principle I).

**Independent Test**: run the example validator and the tool-description checks on the definition, binding and fixtures, with one defect planted at a time.

**Acceptance Scenarios**:

1. **Given** the definition, **When** the checks run, **Then** they pass, and each fails on the defect planted for it.
2. **Given** the fixtures, **When** their origin is checked, **Then** each is a published OpenSLO document with its licence vendored beside it.

### Edge Cases

- A file with several YAML documents separated by `---`, and a file with one: both are read.
- A YAML file that is not OpenSLO: the diagram does not claim it.
- An OpenSLO version the binding does not know: the file opens read-only, with one finding naming the version.
- An occurrences-based and a time-slices-based budgeting method: both are shown, and the budget is stated in the method's own terms.
- A calendar-aligned window: the budget is stated for the window's length, and the companion document says how.
- A file that cannot be read as a whole: the last readable content stays on screen, read-only, with one finding, and the file is not written.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** The definition MUST specify element types for the OpenSLO kinds Service, SLI, SLO, DataSource, AlertPolicy, AlertCondition and AlertNotificationTarget, and relation types for each reference between them that OpenSLO defines, including inline definitions.
- **FR-002** The binding MUST read and write OpenSLO documents as OpenSLO defines them, with byte-preserving edits, and MUST keep documents and fields it does not draw as written.
- **FR-003** The diagram MUST claim a YAML file only when it is an OpenSLO document, and MUST leave every other YAML file to other tools.
- **FR-004** An SLO MUST be shown with its target as a percentage, its window and its error budget in time or events, as expressions the definition states.
- **FR-005** The definition MUST state the findings of User Story 3 with their codes and sentences.
- **FR-006** The definition MUST be delivered as every diagram type in `definitions/diagrams/` is: specification, binding, tool description with trace, companion document and fixtures, named from the origin `openslo/slo` as `definitions/diagrams/README.md` describes.
- **FR-007** Fixtures MUST be real published OpenSLO documents under a permissive licence, with the licence file vendored beside them verbatim and read from the source's own statement at acquisition; share-alike licences are refused.
- **FR-008** Where OpenSLO cannot state something the diagram needs, the definition MUST follow OpenSLO and record the gap in the companion document; it MUST NOT extend the format.
- **FR-009** The companion document MUST let a person or an agent write valid OpenSLO documents the diagram opens without a finding.
- **FR-010** The tool catalogue (`docs/tools.md` in the standalone repository and the Notion "Tools" database) MUST list the diagram as *Specified* when this feature's definition merges.

### Key Entities

- **Service, SLI, SLO, DataSource, AlertPolicy, AlertCondition, AlertNotificationTarget**: OpenSLO's kinds, one element type each.
- **Reference**: a named link from one document to another, or an inline definition.
- **Error budget**: derived from an SLO's target, window and budgeting method; shown, never stored.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** The example validator and the tool-description checks pass on the definition, binding and fixtures, and fail on each planted defect.
- **SC-002** Every fixture opens with every document and reference drawn, and writing it back without an edit leaves it byte-identical.
- **SC-003** For every SLO in the fixtures, the error budget shown equals the value computed by hand in the companion document.
- **SC-004** A service level manager unfamiliar with YAML states the target, window and alerting of every objective in a fixture correctly in under five minutes.
- **SC-005** Documents an agent writes from the companion document alone pass OpenSLO's own validator and open without a finding, in at least four of five attempts.

## Assumptions

- The binding targets OpenSLO `openslo/v1`, the version the specification's own repository marks as stable; a later version is a later feature.
- OpenSLO's licence (Apache License 2.0, according to the research) is verified again at acquisition, as FR-007 requires.
- The origin is `openslo/slo`, after the format's owner, as `w3c/rdf` is named after its own. The file extension is the YAML file's own; how the diagram recognises an OpenSLO document is chosen in the plan.
- The first host to build the diagram, and its separate specification, are chosen after this specification is approved.
