# Feature Specification: The Desktop Host on the Site

**Feature Branch**: in `etalii.adp`, `features/032-site-desktop-host`; in `etalii.adp.site`, one branch of this name per pull request, as the plan cuts them

**Created**: 2026-10-20

**Status**: Draft. Only the specification is written; the plan and tasks wait for the maintainer's approval.

**Input**: The maintainer's approval on 2026-10-20 of the proposal in spec 030's thread: "The site's home page and availability tables still list four IDE hosts, and the Notion copy of the glossary needs the same two-line change", with the site's part to be specified as a feature of its own.

## Context

**What exists.** Spec [030-desktop-native-rust](../../specs/030-desktop-native-rust/desktop-native-rust.spec.md) adds a sixth host, the **desktop host** (`etalii.adp.ide.desktop`): the standalone host's tools and workspace as one native application. The glossary ([docs/terminology.md](../../docs/terminology.md)) and the constitution name it as the fifth IDE host (etalii.adp pull request 385), and the site's copy of the glossary and its build table follow (site pull request 200). The rest of the site still knows five hosts: the home page shows four IDE host cards and Notion; every tool's page has an availability table of exactly five rows; the tool catalogue's Host filter offers five hosts; the site's principles name "the four IDE hosts (standalone, IntelliJ, VS Code, Eclipse) and Notion"; and the Notion "Tools" database, from which the site's catalogue is refreshed, has one host column per host.

**What this feature adds.** The desktop host everywhere the site lists hosts, in the site's fixed order directly after the standalone host, with the honest state of a host that has no release and no catalogue of its own yet.

**Why.** The site is ADP's front door and reference (site Principle I). A host the glossary names but the site omits is a broken promise, and the order (standalone, then desktop) tells a visitor that the two are the same workspace in two forms.

**Words.** Those of [docs/terminology.md](../../docs/terminology.md). A **host card** is one entry of the home page's host list; an **availability table** is the per-tool table of hosts on a tool's page; a **host column** is a host's select property in the Notion "Tools" database.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A visitor sees the desktop host among the hosts (Priority: P1)

A visitor on the home page sees six hosts: the five IDE hosts, the desktop host directly after the standalone host, and then Notion. The desktop host's card has an illustration in the style of the others, its name, its state ("Planned" until its first release), a one-line summary, and either a link to something public or a note saying why there is none.

**Why this priority**: the home page is where a visitor learns which hosts exist.

**Independent Test**: build the site and open the home page; count the host cards and read the desktop host's.

**Acceptance Scenarios**:

1. **Given** the built site, **When** a visitor opens the home page, **Then** it shows six host cards in the order Standalone, Desktop, IntelliJ Platform, Visual Studio Code, Eclipse, Notion.
2. **Given** the desktop host's card, **When** a visitor reads it, **Then** its state is given in text, not colour alone, and its heading links to the tools overview filtered on the desktop host.
3. **Given** the desktop host has no public release, **When** a visitor looks for a link, **Then** the card says so instead of linking to an install.

---

### User Story 2 - Every tool says whether it runs in the desktop host (Priority: P1)

On each tool's page, the availability table has a row for the desktop host, directly after the standalone host's. Until the desktop host keeps a catalogue of its own, every row says "Planned" for the tool types the standalone host has, and nothing else.

**Why this priority**: availability per host is what a visitor comes to a tool's page for; a missing row reads as "not available" without saying so.

**Independent Test**: open three tool pages (one the standalone host has working, one prototype, one the standalone host lacks) and read the desktop host's row on each.

**Acceptance Scenarios**:

1. **Given** any tool's page, **When** a visitor reads its availability table, **Then** it has six rows, in the site's host order.
2. **Given** a tool type the standalone host implements, **When** the desktop host has no catalogue, **Then** the desktop host's row says "Planned".
3. **Given** a tool type the standalone host does not implement, **When** the desktop host has no catalogue, **Then** the desktop host's row says what a host without the tool says today.
4. **Given** the desktop host later keeps a catalogue (`docs/tools.md` in its repository, as the other IDE hosts do), **When** the catalogue is refreshed, **Then** the desktop host's rows come from it, as every IDE host's do.

---

### User Story 3 - The catalogue can be filtered on the desktop host (Priority: P2)

In the tools overview, the Host filter offers the desktop host after the standalone host, and filtering on it shows the tool types whose desktop host state is not "Not planned".

**Why this priority**: the filter is how the host card's heading link works (Story 1, scenario 2), but the overview is usable without it.

**Independent Test**: open the tools overview, choose the desktop host in the Host filter, and compare the list with the availability rows of Story 2.

**Acceptance Scenarios**:

1. **Given** the tools overview, **When** a visitor opens the Host filter, **Then** it offers six hosts in the site's host order.
2. **Given** the filter set to the desktop host, **When** the list is shown, **Then** it holds exactly the tool types whose desktop host row is not "Not planned".

### Edge Cases

- A refresh that finds no desktop host column in the Notion "Tools" database: the refresh reports it and the site keeps the derived "Planned" rows, never failing the build silently or dropping the row.
- A tool type added to the standalone host after the desktop host's catalogue exists: the desktop host's row follows its own catalogue, not the standalone host's.
- The desktop host's repository becomes private: the site names it without linking to it, as it does for any private repository.

## Requirements *(mandatory)*

- **FR-001**: The site's fixed host order **MUST** be Standalone, Desktop, IntelliJ Platform, Visual Studio Code, Eclipse, Notion, and every list of hosts on the site **MUST** follow it: the host cards, the availability tables, the Host filter and the build table.
- **FR-002**: The desktop host **MUST** be one of the IDE hosts wherever the site distinguishes IDE hosts from Notion, as the glossary defines it.
- **FR-003**: The home page **MUST** show a host card for the desktop host with an illustration in the style of the other host illustrations, its name "Desktop", its state, a one-line summary sourced from its repository's readme, and a link only to something public.
- **FR-004**: Every tool's availability table **MUST** have a desktop host row.
- **FR-005**: Until the desktop host's repository keeps a catalogue, its row **MUST** be derived: "Planned" for every tool type the standalone host's catalogue lists as working, prototype or read-only, and the standalone host's value otherwise. The derivation **MUST** be stated on the page in the same way the site states other sources.
- **FR-006**: Once the desktop host's repository keeps `docs/tools.md`, the site **MUST** read its rows from it by the same refresh procedure as the other IDE hosts, and the derivation of FR-005 **MUST** stop.
- **FR-007**: The Notion "Tools" database **MUST** gain a host column for the desktop host, after the standalone host's, which the refresh reads and writes like the others.
- **FR-008**: The tools overview's Host filter **MUST** offer the desktop host.
- **FR-009**: The site's principles in `.specify/memory/repositories/etalii.adp.site.md` **MUST** name the desktop host among the IDE hosts, amended in the same change as FR-001.
- **FR-010**: Every place where the site says how many hosts or IDE hosts there are (for example the home page's "five hosts: the four IDE hosts and Notion") **MUST** say six and five.

### Key Entities

- **Host**: a site entry with id `desktop`, name "Desktop", state, summary, illustration, source (repository, path, revision, taken, method, licence) and optional link, as every host entry has.
- **Host availability**: a tool type's state in one host, now with a desktop host value, derived (FR-005) or sourced (FR-006).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of the site's host lists (home page, every tool page, the Host filter, the build table) show six hosts in the order of FR-001.
- **SC-002**: No page of the built site says "four IDE hosts" or "five hosts".
- **SC-003**: For every tool type, the desktop host's availability equals the rule of FR-005 until the desktop host has a catalogue, checked by the site's catalogue check.
- **SC-004**: A visitor reaches the list of tools planned for the desktop host from the home page in one click.

## Assumptions

- **State "Planned".** The desktop host has no release; its card and rows say "Planned" until spec 030's first release, when its state follows its repository like every host's.
- **Illustration.** A new decorative illustration in the style of the host illustrations is drawn for the site; it carries no information.
- **Summary.** Taken from the desktop host's readme, first paragraph, as the other hosts' summaries are taken from theirs.
- **Notion.** Adding the host column to the "Tools" database is done with the maintainer's Notion access, by the plan's procedure.
- **Out of scope.** The desktop host's own catalogue (`docs/tools.md` in its repository) is spec 030's, not this feature's.
