## Context

**What exists.** Spec 028 defined the Hierarchical Requirement Designer in this repository: its specification `hierarchical-requirement.des` in DESL 0.2, its binding `hierarchical-requirement.fbl` in FBL 0.7's `bullets` family, its companion `hierarchical-requirement.md`, the JSON form a document is read into, and the example `web-shop.md` with its registration, all under `definitions/designers/`. Twelve fixture folders, `specifications/fbl/fixtures/hierarchical-requirement-*/`, hold 23 fixtures, eleven of them one folder down, and state the exact bytes of every edit. The languages it rests on are DED 0.2, FBL 0.7 and DESL 0.2. The companion says that these definition files are authoritative: where this specification and they disagree, they win and this specification is amended.

**What this feature adds.** The designer itself, in the standalone host, the first host to build it and the only one in scope (028: FR-063). It is a person's tool for a file an agent also writes: a person reads the requirements of a subject by its structure, edits them in boxes, and discusses them with the agent through numbers, references and assessments, while the agent reads and writes the same Markdown file as text.

**Why it is a feature of its own.** Spec 028 could state in this repository everything a definition can state. What a person sees and does, and the success criteria that need a person or an agent at work, can only be shown in a host. Spec 028's walk of its requirements (T067) left FR-015 to FR-024, FR-036, FR-037, FR-040, FR-042, FR-045 to FR-047 and FR-050 to FR-052 to the host, and five success criteria: SC-001, SC-002, SC-009, SC-010 and SC-011. This feature carries them.

**What the host lacks today.** Spec 028 read the host at `f45a4d50c` (its research R24). The designer family there is the table from end to end, so a second kind of surface is new work. The host reads no `.des`: a developer writes a designer's module from its definition, and a test compares the vocabularies. It has readers for the `json`, `lines`, `xml` and `yaml` families, not `bullets`. Its registration reader stops at a block it does not know. Its conformance corpus is FBL 0.1 with additions up to FBL 0.6. And it refuses to add an existing file as a designer document.

**When.** Spec 025 moves the places this designer plugs into: it joins the three tool families' routers, catalogs and factories. Nothing is built in the host until spec 025 is done and the maintainer gives the word. The plan reads the host again at that point, not at `f45a4d50c`.

**Words.** Those of [spec 028](../../specs/028-hierarchical-requirement-designer/hierarchical-requirement-designer.spec.md): a **subject**, an **item**, a **requirement**, an **assessment**, a **requirement document**, a **person**, an **agent** and a **tool engineer**. A **conformance run** is the host's replay of the FBL fixtures, as FBL section 15 defines it. Other words are those of [docs/terminology.md](../../docs/terminology.md).

## User Scenarios & Testing *(mandatory)*

Spec 028's user stories describe the designer in any host. Each story below is one of them, in this host, with what only this host decides. Each "028" scenario is to be passed in the standalone host as spec 028 states it.

### User Story 1 - Open an agent's requirement document and read it by its structure (Priority: P1)

A person has a Markdown file an agent wrote, with the designer's envelope on its first line. They open it in the standalone host, and it opens in the designer, not in the Markdown editor, with no registration beside it. They read it as one page of boxes, collapse what they do not need, and focus on a deep item.

**Why this priority**: it is the problem spec 028 states, and the slice that gives value alone. It also settles the two things that stop it in this host today: an existing `.md` cannot be added as a designer document, and two tools already claim `.md`.

**Independent Test**: put a hand-written requirement document three levels deep in a workspace, with no registration, beside an ordinary Markdown file and an Agent Behavior Modelling document. Open each, and pass 028's User Story 1.

**Acceptance Scenarios**:

1. 028's User Story 1, scenarios 1 to 5.
2. **Given** a `.md` whose line 1 is the envelope naming `etalii/hierarchical-requirement`, and no registration, **When** the person opens it, **Then** it opens in the designer.
3. **Given** a `.md` without that envelope, **When** the person opens it, **Then** it opens as it does today, in the Markdown editor or in Agent Behavior Modelling when its registration says so.
4. **Given** an existing requirement document, **When** the person adds it to the workspace as a designer document, **Then** the host accepts it and does not change the file.
5. **Given** an envelope that names a later version of DED, **When** the document is opened, **Then** it opens read-only with the reason.

---

### User Story 2 - A person and an agent work on the same file (Priority: P1)

The person keeps the document open while an agent edits the file. The designer shows each change, keeps what was collapsed, and refuses an edit made against a file that has changed. When the person has unsaved edits and the file changes, they choose between reloading and keeping their version. The person learns that undo stops at the agent's write.

**Why this priority**: the second half of spec 028's problem. Without it the designer is a viewer of a file only one party can keep.

**Independent Test**: open a document in the designer and in a text editor side by side, and pass 028's User Story 2 with each kind of edit on each side.

**Acceptance Scenarios**:

1. 028's User Story 2, scenarios 1 to 6.
2. **Given** a collapsed item, **When** an agent moves it to another item in the file, **Then** the designer shows it in its new place, still collapsed.
3. **Given** an edit the person made before an agent wrote the file, **When** the person undoes, **Then** the host says that the history ended with the change from outside, and the file is not written.

---

### User Story 3 - The host passes the designer's conformance run (Priority: P1)

A developer of the host runs its conformance run. It passes every fixture of the `bullets` family, of the declared registration blocks and of the designer's binding, and the host states what it conforms to. The page the person sees in Stories 1 and 2 rests on these readings and edits.

**Why this priority**: the fixtures are the contract of every byte the host writes (028: SC-003, SC-004). They are what makes a second host of this designer build the same thing.

**Independent Test**: run the conformance run with the FBL 0.7 fixtures in the corpus; plant a wrong byte in one expected result and see the run fail there.

**Acceptance Scenarios**:

1. **Given** the fixtures of `specifications/fbl/fixtures/bullets-read/`, `bullets-edits/`, `registration-blocks/` and `hierarchical-requirement-*/`, **When** the conformance run replays them, **Then** every step passes.
2. **Given** one planted defect in a fixture's expected bytes, **When** the conformance run replays it, **Then** it fails at that step.
3. **Given** a registration with a block the binding does not declare, **When** the person changes a setting, **Then** the block is kept as it was and reported as information.

---

### User Story 4 - Start a document and shape the hierarchy (Priority: P2)

A person creates a requirement document in the host. It starts with the definition's template: the legend for agents and a small starting structure. They add entries without a dialog, by the control at the end of an item or by a key from a selected entry, drag an item with everything in it, and delete what does not apply.

**Why this priority**: as in spec 028. Stories 1 and 2 let a person work on a file an agent started; this lets them start one.

**Independent Test**: pass 028's User Story 4, then compare the created file with the binding's template.

**Acceptance Scenarios**:

1. 028's User Story 4, scenarios 1 to 5.
2. **Given** a new document, **When** it is created, **Then** its file is the binding's template with the file's base name as its title, byte for byte, and no registration exists yet.
3. **Given** a selected requirement, **When** the person presses the key for adding, **Then** a requirement appears below it, ready for typing, and the key is the one the host's help names.

---

### User Story 5 - Questions, remarks and warnings stay with what they concern (Priority: P2)

The person sees an icon at the top right of an entry for its open assessments, opens the list, and answers, changes, removes or resolves each. A collapsed item's icon also stands for what it hides.

**Why this priority**: as in spec 028: it moves the discussion from chat to the requirement.

**Independent Test**: pass 028's User Story 5.

**Acceptance Scenarios**:

1. 028's User Story 5, scenarios 1 to 6.
2. **Given** an entry with two open assessments of different kinds, **When** the document is shown, **Then** the icon at its top right is the one for several, not either kind's.

---

### User Story 6 - Refer to another requirement or item (Priority: P2)

While typing a description, the person types `#`, picks an entry from the lookup, and it stands in the text as a box. Selecting the box shows its target.

**Why this priority**: as in spec 028. It needs the numbers and nothing else.

**Independent Test**: pass 028's User Story 6.

**Acceptance Scenarios**:

1. 028's User Story 6, scenarios 1 to 4.
2. **Given** a reference whose target sits inside a collapsed item outside the focused item, **When** the person selects the box, **Then** the focus and the collapsed state change as far as needed to show the target, and the file is not written.

---

### User Story 7 - Tag items and requirements (Priority: P2)

The person tags entries from a list that searches and creates, renames, recolours, reorders and deletes tags, all in the looks of the Knowledge designer, and deletes the registration without losing anything an agent reads.

**Why this priority**: as in spec 028. It is also what narrowing in Story 8 works on.

**Independent Test**: pass 028's User Story 7, and compare the tag field and list with the Knowledge designer's selection property in both themes.

**Acceptance Scenarios**:

1. 028's User Story 7, scenarios 1 to 5.
2. **Given** a requirement document and its registration, **When** the person deletes the registration, **Then** the requirement document stays, and opening it again creates no registration until a setting changes.

---

### User Story 8 - Categorise, set a state, narrow and sort (Priority: P3)

The person sets a requirement's category and state, narrows the page by tag, category, state or an item pattern, sorts the requirements within each item, and stores a filter under a name.

**Why this priority**: as in spec 028, the first to cut.

**Independent Test**: pass 028's User Story 8.

**Acceptance Scenarios**:

1. 028's User Story 8, scenarios 1 to 5.
2. **Given** a filter that hides an entry with a finding, **When** the person selects the finding, **Then** the entry is shown.

---

### Edge Cases

- A requirement document is also registered as an Agent Behavior Modelling document: the envelope decides, and the designer opens it.
- The person adds an existing `.md` that has no envelope as a requirement document: what the host does, refuse or write the envelope, is the plan's, and the file is never changed without the person's action.
- The registration is deleted while the document is open: the designer goes on with default colours and order, and creates a new registration with the next setting.
- An agent writes the file while the person drags an entry: the drop is refused as an edit against a changed file, and the person is told.
- The host does not support a surface kind or an FBL family a document needs: the document opens read-only with the reason, if at all.
- A document of 100 items and 500 requirements is focused deep: the trail and the page still follow within the time of SC-003.

## Requirements *(mandatory)*

Each requirement names the requirement of spec 028 it carries, as "028: FR-0xx".

### Functional Requirements

#### Recognising and opening a document

- **FR-001**: The host MUST offer the designer type under the name `Hierarchical Requirement Designer` wherever it shows a tool type's name (028: FR-001).
- **FR-002**: The host MUST recognise a `.md` as a requirement document by its envelope on line 1 alone, without a registration, and open it in the designer ahead of the Markdown editor and Agent Behavior Modelling.
- **FR-003**: The host MUST let a person add an existing requirement document to the workspace as a designer document, without refusing because the file exists and without changing it.
- **FR-004**: The host MUST keep a requirement document when its registration is deleted, MUST open it without one, and MUST create the registration only with the first setting the person changes, outside the undo history (028: FR-005; FBL section 8.4).
- **FR-005**: The host MUST create a new requirement document from the binding's template, byte for byte, with the file name the person gives; its title is the file's base name, which the template writes (028: FR-006, FR-007).

#### What the person sees

- **FR-006**: The host MUST show the whole document as one page that scrolls from top to bottom, with no separate tree beside it (028: FR-015).
- **FR-007**: The host MUST draw an item as a box with its requirements and then its sub-items to its right, as high as what stands to its right, with neighbouring boxes sharing their borders (028: FR-016).
- **FR-008**: The host MUST show as many levels as fit the page's width, MUST mark an item whose deeper levels do not fit, and MUST let the person make any item the left edge of the page, with a trail of the items above it that leads back to each of them; focus MUST NOT be stored (028: FR-017).
- **FR-009**: The host MUST show every entry's number beside its title, its tags below the title and its description under it (028: FR-009, FR-018).
- **FR-010**: The host MUST offer a control to the left of every title that collapses the entry to its number, title, tags and assessment icon, and MUST show the same entries collapsed when the document is opened again; collapsing is not an undo step (028: FR-019, FR-020).
- **FR-011**: The host MUST draw the designer in the Knowledge designer's looks, in both themes: its colours, typography and spacing, tags as its rounded tags, and its searchable lists that also create, outside a table as inside one (028: FR-021).

#### Editing

- **FR-012**: The host MUST let the person add an item or a requirement, without a dialog, by a control at the end of every item's content and by one key from a selected entry, which places the new entry directly below it ready for typing; the host's help MUST name that key (028: FR-022).
- **FR-013**: The host MUST let the person drag an item with everything in it, or a requirement, to another item or another place (028: FR-023).
- **FR-014**: The host MUST ask for confirmation before deleting an entry that contains anything, or that a reference or an assessment names (028: FR-024).

#### Assessments and references

- **FR-015**: The host MUST show at the top right of an entry the icon of the kind of its one open assessment, one icon for several when it has more, and a way to add the first when it has none, and a collapsed item's icon MUST also stand for the open assessments of everything inside it (028: FR-036).
- **FR-016**: Pressing the icon MUST open the assessments it stands for as a list, each with the entry it names, in which the person adds, changes, removes and resolves each (028: FR-037).
- **FR-017**: Typing `#` in a description MUST open a lookup of the requirements and items of the same document, narrowed by number or title as the person types (028: FR-040).
- **FR-018**: Selecting a reference box MUST show its target, changing focus and expanding what hides it as far as needed, without writing the file (028: FR-042).

#### Narrowing and sorting

- **FR-019**: The host MUST let the person narrow the page by tag, by category, by state and by an item title pattern with `*` and `?` in any case, and MUST show each requirement that remains with the items that contain it (028: FR-045, FR-046).
- **FR-020**: The host MUST let the person sort the requirements within each item by number, title, category or state, without changing the order in the file (028: FR-047).
- **FR-021**: A finding MUST stay listed when a filter hides its entry, and selecting it MUST show the entry.

#### The file under two writers

- **FR-022**: When the file changes outside the designer, the host MUST read it again and show the change without being reopened, keeping what was collapsed for entries matched by number (028: FR-050).
- **FR-023**: When the file changes outside the designer while it holds unsaved edits, the host MUST tell the person and let them choose between reloading and keeping their version (028: FR-051).
- **FR-024**: The host MUST refuse an edit made against a file that has changed since it was read, as FBL 0.7 section 7.2 states, MUST tell the person, and MUST NOT merge (028: FR-052).
- **FR-025**: When a change from outside ends the undo history, as FBL section 7.3 states, the host MUST tell the person so the first time they undo past it.

#### What the definition states

- **FR-026**: The host MUST make the model change of `hierarchical-requirement.des` for each gesture in the companion's table of gestures and operations, and write the bytes the fixtures state for it (028: FR-025 to FR-035, FR-038, FR-039, FR-041, FR-043, FR-044, FR-048, FR-049).
- **FR-027**: The host MUST report each finding of the companion's "What reading reports" at its place, keep the bytes it names as written, and keep every other entry editable; a file it cannot read at all MUST be shown read-only with one finding and MUST NOT be written (028: FR-053 to FR-055).
- **FR-028**: The host MUST read and write the registration's declared blocks as the binding declares them, and MUST keep a block it does not declare as it was, reported as information (FBL 0.7 section 8.1).

#### Conformance

- **FR-029**: The host MUST state the FBL families it supports, `bullets` among them, and MUST pass every fixture of those families in its conformance run, the FBL 0.7 fixtures that spec 028 added among them (FBL section 15.1).
- **FR-030**: The host MUST state the DESL surface kinds it supports, `hierarchy` among them, and MUST open a document of a kind it does not support read-only, if at all, with the reason (DESL section 11).
- **FR-031**: The host MUST recognise a definition by its envelope, check its DED version, open a later version read-only, and never change an envelope (DED sections 4 and 7).
- **FR-032**: The `hierarchy` surface MUST be the host's shared work, so that a later designer type of that kind needs no surface code of its own in its module.

### Key Entities

As in spec 028, with two of this host's own:

- **Designer document**: what the host lists and opens. A requirement document is one by its envelope, with or without its registration.
- **Conformance corpus**: the fixtures the host's conformance run replays. It holds today FBL 0.1 with additions up to FBL 0.6, and gains those of FBL 0.7.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On one real requirement document, a person finds and judges the requirements of one part of the subject, and says how they fit with the rest, in less time in the designer than in the same file read as text. Both times are measured (028: SC-001).
- **SC-002**: At least nine in ten changes an agent makes to a requirement document over the first four weeks of real use are read without a finding and without the person repairing the file by hand (028: SC-002).
- **SC-003**: A requirement document of 100 items and 500 requirements opens within two seconds and shows an agent's change within two seconds (028: SC-009).
- **SC-004**: The maintainer keeps the requirements of one real subject outside this repository in a requirement document for four weeks and prefers it to the text (028: SC-010).
- **SC-005**: A second person, other than the maintainer, keeps the requirements of a real subject this way. This adds to success and is not a condition for it (028: SC-011).
- **SC-006**: The host's conformance run passes every fixture of `bullets-read`, `bullets-edits`, `registration-blocks` and `hierarchical-requirement-*`, and fails on a planted defect (028: SC-003, SC-004).
- **SC-007**: For every fault in the `hierarchical-requirement-faults` fixture, the person sees either one finding at one bullet with everything else editable, or a read-only page with one finding (028: SC-005).
- **SC-008**: A document whose registration is deleted and created again opens with every tag, category, state, reference and assessment it had (028: SC-006).
- **SC-009**: A requirement document written from the companion alone, by a person or by an agent, opens in the designer without a finding other than `std.missingId` for an entry written as `ITEM-NEW` or `REQ-NEW`, as the companion tells writers to (028: SC-007).

## Assumptions

- **The definition files win.** Where this specification and `definitions/designers/hierarchical-requirement.*` disagree, the definition wins and this specification is amended, as the companion says.
- **Building waits.** No task of this feature starts in the host before spec 025 is done and the maintainer gives the word. The plan reads the host at that point.
- **The module is written from the definition**, as the Knowledge designer's was. A host library that reads `.des` files is not part of this feature.
- **Undo ends at an agent's write**, as FBL section 7.3 states. The host keeps that rule and tells the person (FR-025), rather than keeping a history across a change it did not make.
- **The key for adding, the icon for several assessments, how focus is offered, the mark of an item whose levels do not fit, the trail's looks and the wording of a refusal and of the choice** are the host's. Spec 028 fixed only the behaviour of each (host-handoff, What the host settles).
- **An existing `.md` without the envelope** is not a requirement document. Whether adding one as such is refused or writes the envelope with the person's consent is the plan's.
- **SC-001 is measured on the same document and task twice**: once as text in an editor, once in the designer, by the same person, at least a day apart.
- **The first real subject is the maintainer's to name.** It is not this repository's or the standalone host's own specifications.
- **SC-003's size is a planning figure**, as in spec 028.

## Out of Scope

- Hosts other than the standalone host. Visual Studio Code and IntelliJ implement FBL 0.7 and DESL 0.2 when a feature brings this designer to them.
- Changes to a specification language or to the definition. What the work finds wrong in them comes back to this repository as a feature of its own, or as a correction to spec 028's files.
- Agent Behavior Modelling's move onto the `bullets` family. The host keeps its plugin.
- A host library that interprets `.des` files.
- Merging the edits of two writers, rich text in a description beyond the reference box, and references that leave the document (028: Out of Scope).

## Verbatim Constraints

- `Hierarchical Requirement Designer`: the name users see.
- `ITEM-000x`: an item's number.
- `REQ-000x`: a requirement's number.
- `#`: what the person types in a description to open the lookup of requirements and items.
