# Feature Specification: An Insert Applies a Binding's Empty Rule

**Feature Branch**: `features/026-fbl-insert-empty`
**Created**: 2026-10-12
**Status**: Implemented as FBL 0.6 ([plan.md](../../specs/026-fbl-insert-empty/plan.md), [tasks.md](../../specs/026-fbl-insert-empty/tasks.md))
**Input**: Finding D9 of [spec 025](../../specs/025-standalone-code-structure), row B-09 of its [behaviour-change register](../../specs/025-standalone-code-structure/behaviour-changes.md). The JSON and YAML families of `etalii.adp.ide.standalone` disagree on whether a new entry gets a key for an attribute whose value is empty, and FBL 0.5 does not say which is right. The maintainer ruled on 2026-10-12, on a decision card in the project thread, that FBL is amended so that an insert applies the binding's `empty` rule, with the same defaults as a set.

## Context

An attribute binding's `empty` option (FBL 0.5 section 5.2) says what **setting** an attribute to its empty value (the empty string, the empty list, null) does to an existing entry: `remove` takes the key out, `keep` writes the empty value, `refuse` refuses the edit. `keep` is the default for strings.

When a new entry is **added**, section 6.2 says only that "a key the new entry has no value for is left out". It does not say whether an empty value is a value. Two implementations of the same specification read it two ways. In `etalii.adp.ide.standalone` at commit `af69899`:

- the YAML family (`YamlFamily.WireValue`) leaves the key out when the value is empty, unless the binding says `empty: "keep"`; a string attribute without `empty` is therefore left out on insert, although setting it to empty later would keep it;
- the JSON family (`JsonFamily.WireValue`) writes every value that is not null, so an empty string becomes `"key": ""` whatever the binding says, and only null is left out.

So the same tool type adds a different entry depending on the format its body is in, and in YAML an entry looks different after an add than after an add followed by an edit to the same value. A third host implementing FBL from the document has nothing to go on.

Computed values are not part of the question: FBL's schema allows a slot only one kind (`oneOf` in `$defs/AttributeBinding`), so a binding with a `value` has no `key` and is never written.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A new entry follows the same empty rule as an edit (Priority: P1)

A tool engineer declares `empty` on an attribute binding once, and a user who adds an element with that attribute empty gets the same text as a user who adds it with a value and then empties it.

**Why this priority**: it is the whole of the gap. Without it a host must guess, and the two hosts that guessed guessed differently.

**Independent Test**: a fixture pair, one body in YAML and one in JSON, bound by bindings that differ only in their family, adds an entry with one empty attribute under each of `keep`, `remove` and no `empty`, and states the splices; both bodies get the same keys.

**Acceptance Scenarios**:

1. **Given** an attribute bound with `empty: "keep"`, **When** an entry is added with that attribute empty, **Then** the new entry has the key with the empty value, written as section 6.3 writes that value.
2. **Given** an attribute bound with `empty: "remove"`, **When** an entry is added with that attribute empty, **Then** the new entry has no such key.
3. **Given** an attribute bound with `empty: "refuse"`, **When** an entry is added with that attribute empty, **Then** the add is refused with that reason and nothing is written (section 6.4).
4. **Given** a string attribute whose binding does not declare `empty`, **When** an entry is added with that attribute empty, **Then** the key is written with the empty value, because `keep` is the default for strings on a set too.
5. **Given** an attribute the add gives no value at all, **When** the entry is added, **Then** its key is left out, whatever `empty` says, as section 6.2 already says.
6. **Given** the same tool type bound to a YAML body and a JSON body, **When** the same entry is added to each, **Then** both new entries have the same keys.

### User Story 2 - A host can be checked against it (Priority: P2)

A host implementer runs the FBL conformance fixtures and learns whether their insert follows the rule, without reading another host's code.

**Why this priority**: the disagreement went unnoticed because no fixture adds an entry with an empty attribute.

**Independent Test**: the new fixtures replay through `python .github/scripts/validate-examples.py`, and a planted wrong splice in one of them makes it fail.

**Acceptance Scenarios**:

1. **Given** the new fixtures, **When** the validator runs, **Then** their splices and inverses replay to the stated bodies.
2. **Given** a host that leaves out a key the fixture keeps, **When** it runs the fixture, **Then** its splices differ from the fixture's.

### Edge Cases

- **A binding that refuses an empty value on a new entry.** With `refuse`, a tool cannot create the element until the value is given. A tool engineer who wants a new element to start empty declares `keep` or `remove`, or gives the attribute a default in the tool type's specification.
- **An attribute written through `emit` rather than `keys`.** Section 6.2 already has its own rule for `emit`: an optional segment `[ … ]` is written only when every placeholder in it is non-empty. This feature does not change it.
- **An attribute reached through `child`.** Its value is written by the attribute's `create` after the entry exists (section 5.2), which is a set; the set's rule already applies.
- **A non-string attribute without `empty`.** Section 5.2 names a default only for strings. This feature does not add one: an insert does what a set does for that attribute, so the two cannot differ.
- **An id, a source and a target.** They are not attribute bindings and have no `empty`; this feature does not touch them.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Section 6.2 of the FBL specification **MUST** say that a key of a new entry whose attribute is given its empty value is written or left out by that attribute binding's `empty` rule: `keep` writes the empty value, `remove` leaves the key out, `refuse` refuses the add.
- **FR-002**: The defaults **MUST** be those of a set (section 5.2), so that one binding never gives a different entry for an add than for an add followed by a set to the same value.
- **FR-003**: Section 6.2 **MUST** keep its rule that a key the new entry has no value for is left out, and **MUST** say that an empty value is a value for this purpose.
- **FR-004**: Section 5.2's description of `empty` **MUST** say that it applies to an insert as well as to a set.
- **FR-005**: The refusal **MUST** be listed with the other reasons a change cannot be planned in section 6.4.
- **FR-006**: The conformance fixtures **MUST** include an add with an empty attribute under `keep`, `remove`, `refuse` and no `empty`, in the YAML family and in the JSON family, with the same keys in both.
- **FR-007**: The change **MUST** be a new FBL version, with the status paragraph saying what it changes and that every valid 0.5 document stays valid, and naming the reading 0.5 left open that 0.6 settles.
- **FR-008**: No other specification language changes. DISL and DESL already define an attribute's empty value; FBL decides only how it is written.

### Key Entities

- **Empty value**: the empty string, the empty list or null, as section 5.2 already defines it for `empty`.
- **No value**: an attribute the add does not give at all. Its key is left out.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A reader of section 6.2 alone can say, for each of `keep`, `remove`, `refuse` and no `empty`, whether a new entry gets the key.
- **SC-002**: The fixture pair passes the validator, and fails it with one planted wrong offset.
- **SC-003**: Every existing example and fixture still passes the validator unchanged.
- **SC-004**: Row B-09 of spec 025's register can point at the section that settles it, so that T216 there has a rule and a guard to implement against.

## Assumptions

- The maintainer's ruling of 2026-10-12 decides the meaning; this feature only writes it down.
- The hosts change under their own specifications. `etalii.adp.ide.standalone` does so in spec 025's T216, with the fixture pair as its guard; Visual Studio Code and IntelliJ under their FBL implementation specs, 009 and 010.
- None of the existing example bindings adds an entry with an empty attribute in a fixture, so no existing fixture changes its splices.
