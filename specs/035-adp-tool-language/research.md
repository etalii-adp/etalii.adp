## R2. The specification's name and place: `specifications/atd/`

- **Decision**: the ADP tool language is a specification of this repository in `specifications/atd/`, with its document `ATD-specification.md` titled *ATD, the ADP Tool Language*, version **0.1, Working Draft**, its schema `atd.schema.json` (`$id` `https://etalii.net/adp/atd/schema/0.1/atd.schema.json`), its grammar in `specifications/atd/grammar/` (R3), its examples `*.atd` beside the document, broken variants under `specifications/atd/refused/` with their expected findings, the capability contracts under `specifications/atd/capabilities/` (R14), the generated highlighting grammars under `specifications/atd/highlighting/` (R12) and the guide `ATD-guide.md` (FR-104). The version key is the file's first construct, `atd 0.1` (R5). The language's prose name stays "the ADP tool language"; ATD is its acronym, as DISL is the Diagram Specification Language's.
- **Rationale**: the constitution's *Structure and Naming* uses one lowercase name for the folder, the schema, its `$id`, the version key and the extension. The extension is `.atd` (Q4), so the name is `atd`; a second acronym ("ATL") would break the rule for no gain. FBL is the precedent for a language that serves every kind and sits beside the six.
- **Alternatives considered**: `specifications/adp/` (refused: `.adp` is already the registration file's extension); `specifications/atl/` with extension `.atd` (refused: two names for one format).

## R3. The grammar: a stated subset of Lark notation, in modules that build one table

- **Decision**:
  - The grammar is written in **ATD grammar notation**, a subset of Lark's grammar language that the ATD specification states normatively: rules and terminals; `?rule` (inline when single child) and `_rule` / `_TERMINAL` (filtered); the EBNF operators `?`, `*`, `+`, `[ ]` and grouping; aliases `-> name`; anonymous string terminals; terminal priorities `.n` on terminals only; `%ignore`; `%import` between the language's own modules; `%declare` is not admitted. Templates, rule priorities, `%override`/`%extend`, Lark's `common` library and regex flags are not in the subset. Terminals use the regex subset of R4.
  - The grammar has these modules in `specifications/atd/grammar/`: `atd.lark` (the root: the header and the three kinds' tool constructs), `core.lark` (identity, origin, imports, element types, attributes, ids, enums, constraints and findings, operations, hooks, actions, reasons and messages, localized text, documentation, settings), `cel.lark` (CEL's expression syntax, R6), `script.lark` (R13), `canvas.lark` (the diagram surface: coordinates, placement, snapping, notation, themes, toolbox, context tools, forms, layout), `form.lark` (the designer surface: tables, hierarchies, columns, cells, views, value types, conversions), `text.lark` (the editor surface, from what the five editors do, R18), `binding.lark` (FBL's constructs, registration, and the grammar family of R15) and `notation.lark` (the grammar notation itself, needed by R15). They compose by `%import` into **one** grammar and one LALR(1) table.
  - Which constructs a kind admits is a check of the checker (FR-005), not a split of the grammar: a designer that declares a relation parses, and is refused at the relation (spec story 1 scenario 2).
  - `.github/scripts/atd-grammar.py` in this repository builds the grammar with Lark in `parser='lalr', strict=True` (strict mode fails on every shift/reduce and reduce/reduce conflict and, with `interegular` installed, on every pair of terminals that can match the same text), lints the notation and the terminals against the subsets, writes the flattened single-file grammar of R11, writes the highlighting grammars of R12 and, with `--check`, fails when a committed generated file differs from what it would write. `lark` and `interegular` are pinned in `.github/scripts/requirements-atd.txt` at the releases current when the task runs.
- **Rationale**: FR-002 names Lark notation and strict LALR(1). A *stated* subset is what makes the notation implementable outside Python (R8): Lark's full grammar language has features (templates, rule priorities under Earley, regex flags) whose meaning is Lark's code. One table with kind checks keeps the grammar conflict-free across kinds and gives the findings of scenario 2 at the construct instead of a syntax error.
- **Alternatives considered**: one grammar per kind (refused: three tables, three conflict checks, and FR-004's shared core repeated); ANTLR or tree-sitter notation (refused: FR-002 names Lark; tree-sitter is GLR, not LALR(1)); all of Lark (refused: not implementable from the document).

## R4. Lexing: contextual, longest match, FBL's regex subset, soft keywords

- **Decision**:
  - Terminals are written in FBL's common regex subset (FBL §2.5) without anchors, named groups and lazy quantifiers, which a token has no use for (FR-009). One subset then serves FBL and ATD, and every host already has a matcher for it (the desktop host's `adp-cel` `BoundedRegex`, VS Code's `regexSubset.ts`).
  - The lexer is **contextual**, as Lark's LALR lexer is: in each parser state only the terminals that state can shift, and the `%ignore`d ones, are candidates; among them the longest match wins, then the higher terminal priority, then a string terminal over a pattern terminal. The ATD specification states this as the lexing rule, so that a lexer written from the document tokenizes as Lark does.
  - **Keywords are soft** (FR-008): a keyword is an anonymous string terminal that the contextual lexer offers only where the grammar can shift it. Where a name is expected and a keyword is not, the same word is a `NAME`. Where both could follow (a member list, whose members start with a keyword and some of which may start with a name), the grammar's `name` rule lists the keywords that may appear there (`name: NAME | "label" | "default" | …`), and strict mode proves the result conflict-free. CEL's reserved words stay reserved inside CEL, as CEL requires; outside CEL they are names.
  - Names are DISL's SimpleId (`[A-Za-z_][A-Za-z0-9_]*`), so that every name is a CEL identifier; dotted names are QualifiedIds; an origin `<vendor>/<type>` with its hyphens (`c4/system-landscape`) is its own terminal, offered only where an origin is expected.
  - The later-version edge case (a keyword added by a later version that an existing file uses as a name) is met by FR-101: a file is read with the grammar of the version it declares (R5), so a new keyword never reaches an old file.
- **Rationale**: soft keywords are the only way to give FR-008 and a strict LALR(1) table together, and the contextual lexer is what makes them cheap. Reusing FBL's subset applies Principle I to regexes.
- **Alternatives considered**: reserved keywords with an escape (`` `label` ``) (refused: FR-008 asks for no escape); a non-contextual lexer with a keyword table (refused: it turns every keyword into a reserved word).

## R5. The header, versions and kinds

- **Decision**: every `.atd` file starts with `atd <major>.<minor>`, followed in the root file by the tool construct `diagram|designer|editor <origin> version "<semver>" { … }` and in every other file of a description by `part of <origin>` (FR-012). A reader selects the grammar of the declared version before it parses anything else: the header is the one construct every version of the grammar MUST keep. A version the reader does not know is refused with a finding naming both versions (spec edge case). While the language is 0.x, the Build workflow keeps each released minor's grammar beside the current one (`grammar/0.1/`, `grammar/0.2/` …), and every `.atd` in the repository is checked under its declared version and, per FR-102, under the new version before it is released.
- **Rationale**: Principle IV and FR-101; the root/part split gives FR-012 a syntax the checker can resolve without a separate manifest.
- **Alternatives considered**: a version inside the tool construct (refused: a reader would have to parse with an unknown grammar to find out which grammar to use).

## R6. Values and CEL inside the grammar

- **Decision**:
  - One rule for every value position (FR-006): a bare word, number or quoted string is a literal; `( … )` holds a CEL expression; `@name` is a reference to an attribute (two-way where the position allows it, as DISL's `{attribute}`); `$name.path` is a theme token; `#name` is a parameter. Positions that only ever take an expression (`when`, `rule`, a script's conditions and right-hand sides, binding guards) take CEL without parentheses. DISL's four embeddings (DISL §2.5: Expression, Bindable, GeomExpr, the action expression in which a literal string must be written `"'Untitled'"`) map onto this rule; none survives as a form of its own. A geometry value is an expression in parentheses or a literal length (`50%`, `12`).
  - `cel.lark` carries CEL's expression syntax (the CEL specification's grammar: conditional, `||`, `&&`, relations including `in`, additive, multiplicative, unary, member access, index, calls, the macros as calls, list and map literals, message construction, all literal forms), rewritten for LALR(1) with the precedence levels CEL defines. Expressions are therefore parsed, coloured and type-checked as part of the description (FR-007).
  - The CEL environment of each position (DISL §12.3's contexts, DESL's, FBL §2.4's variables) is the checker's: the ATD specification lists, per position, the variables and functions in scope and the expected result type.
- **Rationale**: parentheses are the smallest marker that keeps an expression and a bare word apart in an LALR(1) grammar, and they are already CEL's own grouping; `@`, `$` and `#` are unused by CEL, so no CEL text is ambiguous with them.
- **Alternatives considered**: `=`-prefixed expressions (refused: `key: = expr` reads as an assignment); expressions in strings as today (refused: FR-007).

## R7. Settings: one `key: value` form, checked by schema

- **Decision**: the open vocabulary (strokes, fonts, layout options, persistence details, `x-` keys) is written as `key: value` pairs and nested `{ … }` maps whose values follow R6. The grammar knows only the form; the checker validates the settings of each construct against the `$defs` of `atd.schema.json` that the ATD specification names for that construct, which reuse DISL's, DESL's and FBL's own `$defs` for the same settings (`Stroke`, `Font`, `LayoutConfig`, `TextDefaults` …) by reference.
- **Rationale**: FR-011, and Principle I: a stroke has one schema, DISL's, whether it is written in JSON or in ATD.
- **Alternatives considered**: a grammar rule per setting (refused: every new layout option would be a grammar change and a new keyword).

## R8. Where the language is implemented: once, in Rust, in the desktop host

- **Decision**: the parser, checker, formatter, script interpreter, binding engine glue and language server are written once, in Rust, as crates of `etalii.adp.ide.desktop` (R9). The VS Code and IntelliJ language servers are that same code (R10, R11). This repository keeps no second checker: its Python scripts build and lint the grammar with Lark, check the generated files, and validate JSON (trees, findings, traces, fixtures) against `atd.schema.json`; the checking of every `.atd` in the Build workflow is done by the Rust checker (R20).
- **Rationale**: FR-043 asks for the desktop runtime to serve the desktop language server as a library; FR-054 asks every language server to report the checker's diagnostics. One implementation meets both by construction, where three would repeat the situation the research found (three DISL interpreters, three FBL libraries of 32,000 lines). The desktop host is Rust already, its core crates depend on no UI toolkit (its Principle III), and it already has the engines a tool description lowers onto (`adp-cel`, `adp-fbl`, `adp-disl`, `adp-desl`, `adp-scene`, `adp-history`).
- **Principle II still holds**: the ATD document, the grammar, the schema and the examples with their expected findings are complete without the Rust code; an implementer can build another checker from them, and the refused corpus with its expected findings is the contract any checker must meet. The single implementation is a choice for phase 1, not a property of the language.
- **Alternatives considered**: a TypeScript implementation shared by VS Code and the desktop host (refused: the desktop host's Principle I forbids a JavaScript runtime); a checker per host (refused: FR-054); the checker in Python in this repository (refused: a second implementation of the static semantics, whose drift FR-054 would then have to chase).

## R10. The language servers: one core, three transports

- **Decision**:
  - **Desktop host**: the shell runs `adp-atd-lsp` in process, on a worker thread, over `lsp-server`'s memory connection, and talks to it in LSP messages like any client. No socket or listener is opened (the desktop host's Principle I). The shell's text editor (`crates/adp-shell/src/editor.rs`, which today has syntect colouring and no completion UI) gains a small LSP client: diagnostics as underlines and in the problems panel, semantic-token colouring, a completion list, hover, go to definition, find references, rename, format and an outline. It serves `.atd` files only; the other editors keep their analyses.
  - **VS Code**: `adp-atd-lsp` compiled to `wasm32-unknown-unknown` with `wasm-bindgen`, about the size of one tool type's module, runs in a Node worker thread of the extension host; the extension connects `vscode-languageclient` (MIT) to it through in-process message transports. The `.vsix` stays one universal file (the VS Code host's constraint: one `etalii-adp-<version>.vsix`, nothing else installed, no network at run time), and its CI, which runs on Linux only, tests the very artifact users get.
  - **IntelliJ**: the platform's own LSP API (`com.intellij.platform.lsp`), declared as an **optional** dependency on `com.intellij.modules.lsp` with its own `config-file`, starts the native `atd-lsp` binary over stdio. The plug-in bundles the binaries the desktop host's CI builds for windows-x64, macos-arm64 and linux-x64. In IDEs without the LSP module (open-source builds of IntelliJ IDEA, Android Studio) the plug-in installs and runs as today, and `.atd` files open as plain text (complexity tracking).
  - **Error recovery** (FR-053): on a syntax error the parser records a finding, then pops states until one can shift a synchronising token (`}`, the start keyword of a construct, the end of a line in a script), skips input to it and continues; the skipped bytes become an error node of the lossless tree. Completion uses the parser state at the cursor, so it works in a broken file. Recovery is the implementation's, informative in the ATD document; what is normative is that the first finding of a refused file is at the position the refused corpus states.
  - **Same diagnostics** (FR-054, SC-005): every transport runs the same core on the same text, so the diagnostics are equal by construction; a test in `adp-atd-lsp` drives the 30-edit walk of SC-005 through the core, and each IDE's tests drive the same walk through the IDE.
- **Rationale**: one implementation, and in each host the platform's own mechanism: an in-process server in a native application, a universal `.vsix` in VS Code, the platform's LSP API in IntelliJ. WebAssembly is used for VS Code only, where the alternative is four native binaries in one package or a platform-specific package, each against that host's constraints. The organization refused WebAssembly three times before (`specs/009-vscode-fbl-implementation/research.md`, spec 006, the standalone steering): each time to *port host code* that could be written in the host's own language. Here the alternative is a second implementation of a checker whose sameness FR-054 requires.
- **Alternatives considered**: for IntelliJ, running the WebAssembly module on Chicory (refused: a JVM dependency the platform does not bundle, whose compiler is still experimental, against SC-006's half second; and the platform's LSP API launches a process in any case); LSP4IJ (refused: EPL-2.0, which the IntelliJ host's `verifyDependencyLicences` rejects, and a second plug-in users must install); a Java language server on LSP4J (refused: EPL-2.0, and a second implementation). For VS Code, the native binaries in a platform-specific `.vsix` per target (refused: four packages instead of one, three of them untested by a Linux-only CI); `@vscode/wasm-wasi-lsp` (refused: needs the WebAssembly Execution Engine extension installed beside it).

## R11. The grammar for model services (FR-090)

- **Decision**: `atd-grammar.py` also writes `specifications/atd/grammar/atd.flat.lark`, the whole grammar in one file with the modules' `%import`s resolved, the names prefixed per module and nothing but ATD grammar notation. The Build workflow checks that the file is accepted by LLGuidance's Lark front end (the `llguidance` Python package, MIT), the context-free constraint engine behind the major model services' grammar-constrained output, pinned like `lark`. The guide (FR-104) says how to hand the file and two examples to an agent; SC-009's trial is a quickstart step.
- **Rationale**: model services that constrain generation to a context-free grammar take one Lark file; LLGuidance is the engine whose acceptance most services share, so its verdict is the check FR-090 can run in CI without calling a service.
- **Alternatives considered**: publishing the modules only (refused: services take one file); a GBNF export (refused: not Lark notation, and fewer services take it).

## R12. Highlighting grammars generated from the grammar (FR-052)

- **Decision**: `atd-grammar.py` generates `specifications/atd/highlighting/atd.tmLanguage.json` (TextMate, for VS Code and as a fallback in any editor that reads TextMate) and `atd.sublime-syntax` (for the desktop host's `syntect`), from the grammar's terminal classes: keywords (every anonymous word terminal), CEL operators and literals, strings, numbers, comments, the sigils of R6, origins, and embedded grammars (R15). Both are committed and `--check`ed. They are checked against the examples where a TextMate or syntect engine runs: in VS Code's unit tests with `vscode-textmate` and `vscode-oniguruma` (MIT, dev dependencies only), and in a `syntect` test in `adp-atd-syntax`, each comparing the scope of every token of every example with the class the ATD lexer gives it. Precise colouring comes from the language servers' semantic tokens (FR-051); the generated grammars colour a file before its server answers.
- **Rationale**: one source for colours; the checks run in the two repositories that have the engines, so this repository's Build stays Python.
- **Alternatives considered**: hand-written TextMate grammars (refused: FR-052 asks for generated ones); a TextMate bundle in IntelliJ (refused: the TextMate plug-in is not one of the platform's common modules; the LSP API's semantic tokens colour `.atd` there).

## R13. The script

- **Decision**:
  - Script functions are declared `fn name(param: Type, …) -> Type { … }` at the top level of a description, with an optional `recursion <n>` bound. Statements: `let` (immutable local), `var` and assignment (mutable locals only), `if`/`else`, `for x in <list or map or range> limit <n>`, `while <cond> limit <n>`, `return`, `fail <message>` (refuses the gesture with a reason), `break`, `continue`, local list and map building, and the action set of DISL §9.4 and DESL §8.2 as statements (`create`, `set`, `unset`, `delete`, `connect`, `move`, `resize`, `retype`, `reparent`, `reorder`, `select`, `reveal`, `notify`, `layout`, `call`, …), each allowed only where a model may change (FR-016). Expressions are CEL (FR-013). The `limit` on loops is mandatory: a loop without one does not parse.
  - **Determinism** (FR-014): the script environment is CEL's with DISL §12.4's library and §12.5's determinism rules, extended to statements: no function reads a clock, randomness, a file, the network, the environment or the host; a `for` over a map visits keys in ascending order of their CEL ordering; arithmetic is CEL's (int64, uint64 and double, with CEL's overflow errors), and `string(double)` formats as CEL's specification says. The checker refuses any call to a function that is not in the library or in the description.
  - **Budget** (FR-015): one step per statement executed, per loop iteration and per CEL call evaluation; the budget is per gesture (one transaction), 100,000 steps by default, settable lower in a description's `limits`, and recursion at most 64 frames unless a function states a lower `recursion`. The numbers are the ATD specification's, chosen as DISL's `limits` and `maxHookDepth` are. Exceeding either stops the call, discards the transaction and refuses the gesture with a finding naming the function (spec story 4 scenario 3).
  - **Changes** (FR-016): actions in a script add commands to the gesture's transaction exactly as DISL's operation actions do (DISL §14.4); a function called from an expression position (a label, a constraint, a derived attribute) may not contain actions, which the checker enforces from the call graph.
  - **Why not an embedded language** (FR-019): the research compared Lua, Starlark, JavaScript, Rhai and FBL-style declarations for the logic the hosts write per tool type. Lua and JavaScript are general-purpose with ambient effects that have to be removed, not added, and their numbers and iteration order differ between implementations; Starlark is deterministic and bounded but brings its own expression language beside CEL, so a description would have two expression syntaxes; Rhai is a Rust library, which would tie the language to one host's implementation language; declarations alone cannot state the small algorithms of *Where the logic goes*. A script designed into the grammar keeps CEL as the one expression language, gets parsing, colouring, checking, formatting, renaming and debugging from the same tooling as the rest of the description, and states determinism and bounds in the language rather than in a sandbox.
- **Rationale**: FR-013 to FR-017 and FR-019; DISL already bounds CEL (its `limits`, its function `recursion`) and defines the action set, so the script adds statements around what exists.
- **Alternatives considered**: loops without a stated limit, bounded only by the budget (refused: a limit written in the text documents intent and lets the checker reject a loop over an unbounded source).

## R14. Capabilities

- **Decision**: a description names a capability with `requires capability <name>@<semver range>` and calls it where its extension point allows (a layout, a router, a reader, an analysis, an arrangement), with arguments in R7's form. The ATD specification's capability catalogue lists each capability with its contract (inputs and outputs as `$defs` of `atd.schema.json`, its laws such as determinism and stability of pinned elements, its fallback) and its conformance fixtures in `specifications/atd/capabilities/<name>/`. The first catalogue holds what the 36 tool types need and the specification's table puts there: Sankey relaxation, self-organising arrange, MSBuild import evaluation, the description-logic renderer, elementary-cycle enumeration if R13's script cannot meet its budget, the readers of Turtle (until R15 replaces it) and SPARQL, and the layout algorithms the hosts implement (layered with a band, tidy tree, mind-map layout, force, row packing). In the desktop host the catalogue is `adp-atd-runtime`'s capability registry, filled from the code the hand-written modules have today (moved, not rewritten), each entry tested against its fixtures. A capability a host does not provide leaves the tool open with the gestures that need it refused (spec edge case).
- **Rationale**: FR-018 and the specification's fourth destination; the assessment note's capability contract (§6.6) is the model. Moving the code keeps parity: the algorithm that produced the reference bytes is the one the capability runs.
- **Alternatives considered**: tool-specific plugins as today (refused: FR-040 forbids tool-specific code; a capability is named by its contract, not by a tool type).

## R15. The grammar family of FBL (FR-080 to FR-082)

- **Decision**: a binding may declare `family grammar` with a grammar in ATD grammar notation inline (`grammar { … }`, parsed by `notation.lark`) or imported from a `.lark` file of the description. The checker builds its table with `adp-atd-grammar` and refuses the binding when it is not LALR(1), naming the conflict (spec edge case). Rules map parse-tree nodes to elements, relations and attributes with selectors over node names (`at statement/triple`), as the `xml` family maps elements; insert and remove templates write new text, as FBL §6.2 does. FBL's guarantees carry over unchanged (FR-081): a node's splice is its byte range in the lossless tree; text no rule maps is kept; reading recovers at the grammar's synchronising tokens so that a body that does not parse is read in part with a finding at its line (story 7 scenario 3). The W3C RDF type's Turtle binding is the first instance, its fixtures recorded from the desktop host's current Turtle reader (R17) (FR-082, SC-010). FBL gains the family as **FBL 0.9**, since a binding is FBL's whether it is written in JSON or ATD; the `.fbl` form of the family takes the grammar as a string or a file reference.
- **Rationale**: the same table builder and lossless tree serve the language and the family, so the family costs a module of rules, not a second parser. The assessment note (§6.5) calls a grammar family a research question because lens alignment is hard; keeping the lossless tree's byte ranges as the splices sidesteps alignment for edits that change a node in place, and the Turtle fixtures decide whether inserts and removals are right.
- **Alternatives considered**: the family in ATD only (refused: a binding has one meaning in FBL, Principle I); Turtle, SPARQL and Structurizr DSL together (refused: SC-010 asks for Turtle; SPARQL stays a capability in phase 1, and Structurizr DSL stays on the `blocks` family it already uses).

## R16. The validation runtime: lowering onto the engines

- **Decision**: `adp-atd-runtime` lowers a checked description onto the desktop host's existing engines rather than interpreting it anew: the model, notation, toolbox, forms, constraints and behaviour onto `adp-disl`'s and `adp-desl`'s in-memory specifications, the bindings onto `adp-fbl`'s `FblBinding`, the notation onto `adp-scene`, editing onto `adp-diagram` sessions and `adp-history` commands. Where ATD has more than DISL, DESL or FBL (script functions, capabilities, the constructs added for the recurring gaps), the engines gain generic extension points: CEL functions resolved to script functions, operations and hooks whose body is a script, capabilities looked up by name in the registry. The runtime has no code for any tool type (FR-040); the 13 diagram modules and the Knowledge designer that the desktop host draws by hand today give their behaviour to descriptions, scripts and capabilities (R14), not to the runtime. The runtime is a library: the validation view (R21), the debugger and `atd validate` use it; the shell's catalogue and tool loading do not (FR-031, SC-002).
- **Rationale**: the engines are what produce the reference behaviour today for the six types they already drive from their `.dis` (timeline, Gartner hype cycle, causal loop, dependency graph, mind map, agent behaviour modelling), so lowering onto them makes parity the default and confines differences to what ATD adds.
- **Alternatives considered**: a new interpreter beside the engines (refused: a fourth implementation of DISL's semantics in the same host).

## R17. Conformance fixtures: from the parity goldens and the desktop host

- **Decision**:
  - A **conformance fixture** extends FBL's round-trip fixture (`$defs/Fixture`, FBL §15.3) with the gestures of the desktop host's parity edit scripts (`parity/scripts/…`: `select`, `action` with `args`, `property`, `move`, `undo`, `redo`) and with the expected readings, findings, splices and drawings after each step (contracts/conformance.md). They live in this repository beside the descriptions, under `definitions/<kind>s/conformance/<type>/<case>/`, so that the desktop host and VS Code validate against the same files (FR-063).
  - **Bytes** come from the standalone host: where the desktop host has goldens recorded by its C# recorder against the standalone host (`parity/goldens/…`), the fixture takes them unchanged with their provenance. **Readings, findings and drawings**, and the bytes of the types and steps without a golden, are recorded from the desktop host at `fe5feec` by `atd record`, which runs the existing modules headlessly on the fixture's documents and gestures. A drawing is the scene in `adp-scene`'s vocabulary (delivered elements with their shapes, labels, positions, styles and drawn primitives), as the `insta` scene snapshots already hold for the mind map, timeline and C4 container; for the types whose scene is drawn in the shell (`crates/adp-shell/src/canvas/*_scene.rs`), the recorder gets the same vocabulary through a recording painter added in the shell.
  - So the **reference host** of SC-004 is the standalone host for bytes, as the desktop host's Principle II and IV already require, and the desktop host for drawings, which the standalone host has no toolkit-free form of. Each fixture records which host and commit produced each part.
- **Rationale**: the specification excludes changes to the standalone host; the desktop host already proves byte parity with it (parity inventory P-001 to P-070), so its goldens and its modules are the reachable record of the reference behaviour.
- **Alternatives considered**: a recorder in the standalone host (refused: the standalone host is out of this feature's scope and plans in its own repository); drawings as screenshots (refused: pixels depend on fonts and GPUs, and the desktop host only inspects screenshots, it does not compare them).

## R18. The tool descriptions and their traces

- **Decision**:
  - Each description is `definitions/<kind>s/<name>.atd` beside the type's `.dis` or `.des` (FR-020; the folders are flat today), split into parts where it is long (`<name>.<part>.atd`). The editors get `definitions/editors/<name>.atd` (the folder holds only a README today). The bindings that live in the standalone repository today and are vendored into the desktop host from there are written as the description's binding part, read from that vendored copy.
  - A **trace** `definitions/<kind>s/<name>.trace.json`, validated against `atd.schema.json` `$defs/Trace`, lists every item of the companion file's gap sections (the companions' headings differ: "What DISL still lacks", "The gaps", "Language gaps", "What the languages cannot state"; the trace names the sections, and every `###` heading and top-level list item under them is an item) and every behaviour taken from host code, each with the host, the file and line range at the reference commit, and the construct, script function, binding rule or capability of the description that states it, or the host's concern it is (FR-022, FR-023). A check in `validate-examples.py` fails when a companion item is missing from the trace or a trace entry names a construct the description does not have (SC-003).
  - The host code read is the desktop host's module for the type (a full port of the standalone host's), with the standalone host's module where the desktop host's is a port marked partial, VS Code's plugins (`abm-markdown`, `freeplane-mm`, `knowledge-views`, `mindmap-layout`, `abm-arrange`, and `project-link-picker`, which the specification's list missed) and IntelliJ's FreeMind module for the mind map.
  - Order: the mind map first, as the vertical slice through every part of the toolchain, then the five other DISL-driven types, the two designers and the five editors, then the 23 types the hosts draw by hand, grouped by their desktop module crates (C4 ×6, Databricks ×3, RDF ×4, and the rest one by one).
- **Rationale**: FR-020 to FR-023; companions differ in shape, so the trace says where their items are rather than the companions being rewritten.
- **Alternatives considered**: rewriting every companion into one heading structure first (refused: churn in 31 files that this feature does not otherwise change, and FR-031's spirit of leaving today's files alone).

## R19. Findings

- **Decision**: findings have codes `ATD<nnnn>` grouped by phase (`ATD0xxx` header and version, `ATD1xxx` syntax, `ATD2xxx` names and imports, `ATD3xxx` kinds, `ATD4xxx` types and CEL, `ATD5xxx` settings against the schema, `ATD6xxx` cross-checks, `ATD7xxx` script, `ATD8xxx` bindings and grammars, `ATD9xxx` validation), a severity (error, warning, information), a file, a 1-based line and a column counted in code points (DISL §8.6, FBL §2.6), an end position, a message in ADP's words, and fixes as text edits. Machine-readable output (FR-091) is JSON, `$defs/Findings` of the schema; the LSP diagnostics carry the same code and fixes as code actions. "Closest existing names" (story 1 scenario 4) are the names in scope within an edit distance of 2 or sharing a prefix of 3, at most five.
- **Rationale**: the existing findings types (`adp-problems::Finding` has severity, message, file, line, column, element, rule) map onto these fields, so the desktop host's problems panel shows ATD findings without a new type.
- **Alternatives considered**: free-text findings (refused: FR-091).

## R20. The Build workflow of this repository

- **Decision**: two new jobs in `.github/workflows/build.yml`:
  - `grammar` (Python 3.13, `requirements-atd.txt`): `atd-grammar.py --check` (strict LALR(1), subsets, the flattened grammar accepted by LLGuidance, the generated files unchanged) (SC-001).
  - `descriptions`: checks out `etalii.adp.ide.desktop` at the branch of the pull request's name when that branch exists there, else at `develop`; builds `adp-atd-cli` (with the Rust cache) against this checkout's `specifications/atd/` (the `build.rs` reads `ATD_SPEC_DIR` before the vendored copy); runs `atd check` on every `.atd` in the repository and on the refused corpus, comparing findings with the expected ones; runs `atd tree` on every example and validates each tree against `atd.schema.json` with Python's `jsonschema`.
  - `validate-examples.py` gains the trace and fixture checks of R17 and R18 (JSON against the schema, companion coverage, fixture files present).
- **Rationale**: FR-100 asks this repository's Build to check every `.atd`; checking it with the one checker, built from the branch that changes the checker together with the language, keeps a language change and its checker change in step without a release in between. Both repositories are public, so the job needs no token.
- **Alternatives considered**: a released `atd` binary pinned by version (refused: a change to the language could not pass until a desktop release existed that understands it, a cycle between the two repositories); a Python checker (R8).

## R21. The validation view, hot reload and the debugger in the desktop host

- **Decision**:
  - A **validation view** in the shell opens a tool description with one of its conformance cases: the left pane is the description's tool running on a working copy (canvas, toolbox, forms, operations and refusals, as the runtime declares them), the right pane the list of differences from the fixture, each linked to the construct that causes it (FR-041). Validation never writes outside a temporary working directory (FR-042), and documents a person has open keep their current tools (story 4 scenario 4).
  - **Hot reload** (FR-044): the view watches the description's files with the existing `adp_hierarchy::Watcher`; a save re-checks and, when it checks clean, re-runs the case; a failing version shows its findings and keeps the last result.
  - The **debugger** works on the validation view's runtime: breakpoints by line in script functions, operations, hooks and binding rules, conditions in CEL; step over, into and out, continue, stop; while paused the frames with their locals and arguments, the call stack back to the gesture, the elements involved, the transaction's collected commands in order, and the budget used (FR-070, FR-071). The interpreter runs the gesture on a worker thread and parks it at a pause; stop discards the transaction (FR-072). Its interface is modelled on the Debug Adapter Protocol's concepts (breakpoints, threads, stack frames, scopes, variables) in `adp-atd-script`'s Rust API, without the wire protocol: no client outside the desktop host needs it in phase 1 (Principle V).
- **Rationale**: the runtime of R16 is a library, so the view, the debugger and `atd validate` share it; parking a worker thread keeps the shell responsive while paused.
- **Alternatives considered**: a DAP server for VS Code to attach to (refused: not asked; FR-070 puts the debugger in the desktop host).

## R22. VS Code: the editor and the validation

- **Decision**: the VS Code host contributes the language `atd` (extension `.atd`, the generated TextMate grammar, a language configuration), starts the WebAssembly language server for it (R10), and adds three commands in the category "ADP": *New Tool Description* (asks the kind, the origin, validated as `<vendor>/<type>`, and the name, then a folder through the platform's dialog; the text comes from the server's `atd/newDescription` request, so it is the core's template and checks clean, FR-060), *Check Tool Description* (asks the server to re-check every file of the description and shows findings in the Problems panel, FR-061; checking also happens as the user types and on save), and *Validate Tool Description* (the server's `atd/validate` request on the description's fixtures, read through `vscode.workspace.fs` and handed to the server as content, showing differences as diagnostics and in an output channel, FR-063). Nothing runs a person's document from `.atd`.
- **Rationale**: the VS Code host's Principle I (commands in the palette under "ADP", findings as diagnostics, the platform's dialogs); the server holds the logic, so validation in VS Code and in the desktop host are the same code on the same fixtures.
- **Alternatives considered**: a custom editor for `.atd` (refused: a tool description is text, edited in VS Code's text editor with language support; "an editor" in the request is met by that and by the creation command).

## R23. The constitution and the glossary

- **Decision**:
  - Constitution **1.8.0** (MINOR), through `/speckit-constitution` as a task of this feature: Principle II's "machine-readable schema for every format" is kept, and *Structure and Naming* adds that a language whose authored form is text rather than JSON carries its grammar in its folder beside the schema (`grammar/`), that its schema describes its parsed tree, that its version key is its first construct, and lists `specifications/atd/` beside FBL as a language serving every kind. The specification's quality checklist left this to the plan's Constitution Check.
  - `docs/terminology.md` defines, before any other document uses them and in the same pull request as the ATD document (FR-103): **ADP tool language** (ATD), **tool description** (`.atd`, the ADP Tool Description), **script**, **capability**, and also **conformance fixture** and **trace**, which the descriptions' files use. A tool description is not a "definition": the glossary keeps "definition" for the documents users create (Q4).
- **Rationale**: the constitution names schemas only; without the amendment the grammar's place is a convention.
- **Alternatives considered**: no amendment (refused: the next text language would have to rediscover the layout).
