# Feature Specification: Export a Causal Loop Diagram as an Animated Flow Page from the Desktop Host

**Feature Branch**: in `etalii.adp`, the specification arrives on `claude/project-thread-mevaun`; in `etalii.adp.ide.desktop`, one branch per pull request, as the plan cuts them

**Created**: 2026-10-31

**Status**: Draft; specified, awaiting the maintainer's approval before the plan

**Input**: The maintainer's request of 2026-10-31: "In terms of the desktop designer, can you create an export button in the command bar that generates these html files from the CLD, and then opens them? This can be done completely outside of the FBL/DISL and ATD approaches. Build a spec so that this can be made nicely. It should be applicable for any CLD, not solely the mental model." "These html files" are the animated page the maintainer asked for on 2026-10-30 for the mental health example, described under Context.

## Context

**What exists.** On 2026-10-30 the maintainer asked for "one single HTML file that shows the CLD in an animated, controllable fashion", flow based like the yFiles process mining showcase, with "a heatmap kinda bottleneck principle" and control over the values. A prototype was made for the mental health example (standalone pull request 755) as one self-contained page: the diagram drawn at its registered positions, dots flowing along each link, a heatmap of where influence piles up, sliders for the variables nobody in the diagram moves, and a chart of the main variables over time. The maintainer accepted it and now wants every causal loop diagram to get one, from a button. The prototype was made by hand, for one document, with a few scenarios written for that document's subject; it is kept outside every repository, in the project's shared files as `mental-health-cld/mental-health-cld-flows.html`, and is the reference for how the page looks and moves.

**Where it lands.** The desktop host (`etalii.adp.ide.desktop`, spec 030) has a ribbon across the top of its workspace, which the maintainer calls the command bar. Its causal loop diagram (`systems/causal-loop-diagram`, files `.cld`) is read and drawn through the diagram's DISL specification and FBL binding, with a small module that keeps the cycle finder, the ring a document opens on and Arrange diagram.

**What this feature adds.** An export button on the ribbon. Pressed while a causal loop diagram is the open document, it writes one self-contained page that animates that diagram as flows of influence, and opens it. The page is generated by the desktop host from the diagram as the host holds it. As the maintainer asked, nothing about it goes through DISL, FBL or ATD: no specification language, binding or tool description gains a construct for it, and no other host has to follow it.

**Words.** A **flow page** is the exported page. A **variable**, a **link** (with its polarity, delay, weight and note) and a **loop** (reinforcing or balancing) are the causal loop diagram's own words. An **external variable** is a variable no link points to. **Influence** is what a link carries from its source to its target in the flow page; a **dot** is one visible piece of it. The **ribbon** is the desktop host's command bar. Other words are those of [docs/terminology.md](../../docs/terminology.md).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - One press turns the open diagram into a flow page (Priority: P1)

A person has a causal loop diagram open in the desktop host. They press Export flow page on the ribbon, and a moment later the flow page of that diagram opens in their browser, already moving.

**Why this priority**: it is the whole request in one gesture; every other story refines what the page shows.

**Independent Test**: open each causal loop diagram example the desktop host carries, and the mental health example, press the button, and see each page open with every variable, link and loop of its diagram.

**Acceptance Scenarios**:

1. **Given** a causal loop diagram is the open document, **When** the person presses Export flow page, **Then** a flow page of that diagram is written and opened with the platform's program for web pages, and the status tells where it was written.
2. **Given** the diagram has unsaved edits, **When** the person exports, **Then** the page shows the diagram as the canvas shows it, edits included, and the file on disk is not touched.
3. **Given** the canvas shows variables at registered positions, at the ring a document opens on, or as the person has just dragged them, **When** the person exports, **Then** the page places every variable where the canvas does, scaled to fit.
4. **Given** the open document is not a causal loop diagram, or no document is open, **When** the person looks at the button, **Then** it is disabled and says why, as every unavailable ribbon button does.
5. **Given** the platform has no program for web pages, or opening fails, **When** the person exports, **Then** the page is still written and the host says where it is, so it can be opened by hand.

---

### User Story 2 - Influence is seen to flow, and delays are seen to hold it (Priority: P1)

The person watches the page. Dots travel along every link from source to target, more of them where the source is higher and the link stronger. On a delayed link they travel slowly, so they bunch up. A variable changes only when influence reaches it.

**Why this priority**: the flow is what the maintainer pointed at in the yFiles showcase, and the reason the page exists.

**Independent Test**: export a diagram with one delayed and one plain link out of the same variable, raise that variable, and see the plain link's target respond first and the delayed link carry many more dots in transit.

**Acceptance Scenarios**:

1. **Given** a link with positive polarity and one with negative polarity, **When** the page runs, **Then** their dots have two distinct colours, the same on every page, and each link shows its polarity sign near its target.
2. **Given** a variable whose level rises, **When** the page runs, **Then** each link out of it carries dots more often, and a positive link pushes its target up while a negative link pushes it down.
3. **Given** a delayed link, **When** the page runs, **Then** it is drawn with the delay mark, its dots take several times longer to arrive than on a plain link, and its effect on the target arrives only as late as its dots do.
4. **Given** a link with a weight, **When** the page opens, **Then** that weight is the link's starting strength.

---

### User Story 3 - A heatmap shows where it piles up (Priority: P1)

The person switches the heatmap between four readings and sees, by colour, which variables and links are bottlenecks.

**Why this priority**: the "heatmap kinda bottleneck principle" is the maintainer's second named requirement.

**Independent Test**: export the mental health example, leave it running for twenty seconds, and see the variables fed by delayed links (exhaustion, dropout) hottest under Backlog.

**Acceptance Scenarios**:

1. **Given** the page is running, **When** the person chooses Backlog, **Then** every variable and link is coloured by the influence in transit towards it, relative to the busiest.
2. **When** the person chooses Pressure, **Then** each variable is coloured by how far it is from where its inputs push it.
3. **When** the person chooses Throughput, **Then** each variable is coloured by the influence arriving per second, relative to the busiest.
4. **When** the person chooses Level, **Then** each variable is coloured by its own level, from 0 to 1.
5. **Given** any reading, **Then** a legend shows the colour scale and one sentence says what the reading means.

---

### User Story 4 - The person controls the values (Priority: P1)

The person moves sliders and sees the system answer: the external variables, the overall dynamics, and any one variable or link they select.

**Why this priority**: control over the values is the maintainer's third named requirement.

**Independent Test**: on any exported diagram, change each control once and see the page respond within a second of simulated time.

**Acceptance Scenarios**:

1. **Given** the diagram has external variables, **When** the page opens, **Then** each has a slider from 0 to 1; a diagram without any shows a sentence saying so.
2. **Given** the dynamics controls, **When** the person changes simulation speed, link strength, the length of a delay, a variable's inertia or the dot density, **Then** the page follows at once, without restarting.
3. **Given** the person clicks a variable, **When** it is selected, **Then** they can push it from outside, up or down, and give it a sudden jump to its highest or lowest level.
4. **Given** the person clicks a link, **When** it is selected, **Then** they can change its strength, add or remove its delay and flip its polarity, and the page shows the link as changed.
5. **Given** controls are in use, **Then** the page offers Pause, Play, Reset (every level back to its start, the controls kept) and Fit, and Reset leaves the controls where the person set them.
6. **Given** anything the person changes in the page, **Then** nothing is written back to the diagram, its registration or any other file.

---

### User Story 5 - Loops and their strength (Priority: P2)

The person sees each loop of the diagram listed with its kind and a live measure of its strength, and traces one on the drawing.

**Why this priority**: the loops are what a causal loop diagram is for; the page is more useful with them, but the flow and the controls stand without.

**Independent Test**: export a diagram with a reinforcing and a balancing loop, and see both listed, both marked on the drawing, and each highlighted on hover.

**Acceptance Scenarios**:

1. **Given** the diagram declares loops, **When** the page opens, **Then** each is listed with its name and its kind, reinforcing or balancing, from the polarities of its links, and marked on the drawing at the middle of its variables.
2. **Given** the diagram declares no loops, **When** the page opens, **Then** the list holds the cycles the desktop host finds in it, named as the host's canvas names them.
3. **Given** the page is running, **Then** each loop shows its current loop gain, and a gain at or above 1 is marked as running away.
4. **When** the person hovers or clicks a loop, **Then** its links and variables are emphasised and the rest dimmed, until the hover ends or the second click.

---

### User Story 6 - What changes over time (Priority: P2)

A chart under the drawing shows the levels of a few variables over the last minute of simulated time.

**Why this priority**: it turns what the person saw flash past into something they can compare, but the drawing alone already shows the levels.

**Independent Test**: export any diagram and see up to seven series, the selected variable's line emphasised.

**Acceptance Scenarios**:

1. **Given** the page opens, **Then** the chart follows up to seven variables, those in the most loops first, each in its own colour with a legend.
2. **Given** a selected variable, **Then** the person can add it to or remove it from the chart, and its line is emphasised while selected.

---

### User Story 7 - The page travels on its own (Priority: P2)

The person mails the page to a colleague, or opens it without a network. It works the same.

**Why this priority**: the maintainer asked for one single file; that is only worth it when the file needs nothing else.

**Independent Test**: export a diagram, move the file to another machine with no network, open it in each of the three mainstream browsers, and see it run.

**Acceptance Scenarios**:

1. **Given** an exported page, **Then** it is one file and fetches nothing: no script, style, font or image from anywhere else.
2. **Given** the same diagram exported twice, **Then** the two files are byte-identical.
3. **Given** the page, **Then** it carries the diagram's title, or its file name when it has none, and the sentence that its numbers come from a simple model of the structure and are not data.

### Edge Cases

- A diagram with variables and no links: the page opens, the variables sit still, and a sentence says there is nothing to flow.
- A link from a variable to itself: drawn as a small loop beside the variable, carrying dots like any link.
- Two links between the same two variables, one each way: drawn apart, so the dots of each stay on their own line.
- A link to or from a variable that is not declared: left out of the page, and the page says how many statements it left out; the host's own findings on the diagram are unchanged.
- Lines the binding cannot read: the page shows what was read, as the canvas does.
- A label holding characters that mean something in a web page (`<`, `&`, quotes, a script tag): shown as text, never run or read as markup.
- A weight of zero, negative or very large: zero gives a link that carries nothing until its strength is raised; a negative weight is read as its size; every weight is limited to the strength slider's range.
- A large diagram (200 variables, 600 links): the page opens and moves smoothly; dots are thinned rather than the page slowed.
- A diagram never saved: exported under the name the tab shows.
- The same diagram exported again while its earlier page is open: the earlier file is replaced and the new one opened, so the person does not collect copies.
- The page in a light or dark system setting: it is readable in both.
- A narrow browser window or a phone: the drawing and the controls stack, and nothing scrolls sideways.

## Requirements *(mandatory)*

### Functional Requirements

#### The button

- **FR-001**: The desktop host **MUST** show an Export flow page button on the ribbon, enabled while a causal loop diagram is the open document and disabled otherwise with the reason, as other ribbon buttons are (spec 030 P-010).
- **FR-002**: The button **MUST** be offered by the causal loop diagram, not named in the frame: the ribbon learns from the open tool type that it has an export, so that another tool type can offer one later without the frame changing (desktop Principle III).
- **FR-003**: Pressing it **MUST** write the flow page of the diagram as the canvas holds it, unsaved edits and current positions included, and **MUST NOT** write to the diagram, its registration or any file beside them.
- **FR-004**: The page **MUST** be written to a folder of the person's own for exported pages, outside the diagram's folder, under the diagram's file name with the extension `.html`; exporting the same diagram again **MUST** replace that file.
- **FR-005**: After writing, the host **MUST** ask the platform to open the page with the person's program for web pages, and **MUST** say in the status where the page was written, whether or not it opened.
- **FR-006**: The button **MUST** be exposed to the platform's accessibility interface with its role, name and state, its name being Export flow page (desktop Principle I).

#### What the page holds

- **FR-007**: The page **MUST** hold every variable with its label, every link with its source, target, polarity, delay, weight and note, and every declared loop with its id, name and kind; with no declared loops it **MUST** hold the cycles the host finds, as in User Story 5.
- **FR-008**: The page **MUST** place each variable where the canvas places it at the moment of export, scaled to fit its drawing area.
- **FR-009**: The page **MUST** be a single file that loads nothing from outside itself, and **MUST** show every text from the diagram as text, never as markup or script.
- **FR-010**: The same diagram, positions and labels **MUST** give a byte-identical page.

#### How the page moves

- **FR-011**: Each variable **MUST** have a level from 0 to 1, starting at 0.5; an external variable's level **MUST** follow its slider.
- **FR-012**: Every other variable **MUST** move towards a target set by its incoming links: each link contributes its source's level as the link carried it, times the link's strength, with its polarity's sign; the sum, centred so that inputs at 0.5 give a target of 0.5 and scaled by the link-strength control, sets the target through a smooth curve between 0 and 1, shifted by the variable's outside push; and the level approaches its target at the pace the inertia control sets.
- **FR-013**: Each link **MUST** send dots at a rate proportional to its source's level and its strength, times the dot density; a dot **MUST** take the travel time of a plain link, or that time multiplied by the length-of-a-delay control on a delayed link; and the influence a link delivers **MUST** be its source's level as it was when the arriving dots set off, so that what is seen and what happens agree.
- **FR-014**: Positive and negative dots **MUST** have two distinct colours; a dot's size **MUST** grow with its source's level.
- **FR-015**: The heatmap **MUST** offer Backlog, Pressure, Throughput and Level, as User Story 3 states, colouring both variables and links on one sequential scale with a legend, Backlog first.
- **FR-016**: Each loop's gain **MUST** be the product, over its links, of the target's sensitivity to that link at the current levels, and **MUST** be shown live, a gain at or above 1 marked.

#### Controls

- **FR-017**: The page **MUST** offer: a slider per external variable; simulation speed, link strength, length of a delay, inertia of a variable and dot density; Pause and Play, Reset and Fit; for a selected variable, its outside push and a jump up and down; for a selected link, its strength, its delay and its polarity; and the heatmap reading.
- **FR-018**: The person **MUST** be able to pan, zoom, drag a variable to another place in the page, and hover a variable or link to read its level, its note and what is in transit.
- **FR-019**: The page **MUST** keep what the person does in it to itself, and closing the page **MUST** forget it.

#### Looks

- **FR-020**: The page **MUST** read in a light and a dark system setting, and **MUST** have no sideways scroll at a phone's width.
- **FR-021**: The page **MUST** say, in one visible sentence, that its numbers come from a simple model of the diagram's structure and are not measurements.

#### Fit with the desktop host

- **FR-022**: The export **MUST NOT** add a construct to DISL, DID, FBL or ATD, nor change a definition in etalii.adp; it is the desktop host's own, kept with its causal loop diagram (the maintainer, 2026-10-31).
- **FR-023**: The parity inventory **MUST** record the export as a desktop-only feature with no standalone counterpart, with the tests that show it.
- **FR-024**: The page **MUST** be an output the person opens in a program of their choosing; the desktop host **MUST NOT** embed, start or need a browser to export (desktop Principle I).

### Key Entities

- **Flow page**: one self-contained web page for one diagram, holding its variables, links, loops and positions, the model of FR-011 to FR-016 and the controls of FR-017.
- **External variable**: a variable no link points to, set by a slider.
- **Dot**: a visible piece of influence on a link, set off at the source and delivered at the target.
- **Heatmap reading**: one of Backlog, Pressure, Throughput and Level, the measure the colours show.
- **Export folder**: the folder of the person's own the pages are written to.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: From the press of the button to the page moving in the browser takes under two seconds for a diagram of 100 variables.
- **SC-002**: Every causal loop diagram example the desktop host carries, and the mental health example, exports to a page holding all of its variables, links and loops, checked by count.
- **SC-003**: A page of 200 variables and 600 links keeps a smooth animation (30 frames a second or more) in the current release of each of the three mainstream browsers on an ordinary laptop.
- **SC-004**: An exported page opened with the network off makes no request and runs as it does online.
- **SC-005**: Exporting the same diagram twice gives byte-identical files.
- **SC-006**: A label made of web-page markup and script shows as its own text in the page, and runs nothing.
- **SC-007**: Shown the exported page of the mental health example beside the hand-made prototype, the maintainer finds it does everything the prototype does apart from its subject-specific scenarios.

## Assumptions

- **"The desktop designer" is the desktop host**, `etalii.adp.ide.desktop`, and "the command bar" is its ribbon. The standalone host gets no button from this feature.
- **The export folder** is a folder of the person's own for exported pages, so that pressing the button again leaves no copies in a repository; the plan names it per platform. Writing beside the diagram instead, or asking each time, is the maintainer's to choose before the plan.
- **The prototype's scenarios are left out**: they were written for the mental health subject and have no counterpart for an arbitrary diagram. The generic page starts every external variable at 0.5.
- **The model is the prototype's**: simple, smooth, and the same for every diagram. It shows how the structure behaves, not a calibrated simulation; no units, stocks or equations are read from the diagram.
- **The page is not a tool**: it is not a diagram, designer or editor of ADP, reads no definition, and is not listed in `docs/tools.md`.
- **Nothing is shared with other hosts**: if a second host wants a flow page later, that is a feature of its own, which may lift the generator into something shared then.

## Out of Scope

- An export button in any host other than the desktop host.
- Flow pages for tool types other than the causal loop diagram, though FR-002 keeps the door open.
- Scenarios, saved settings, or anything written back from the page.
- A model with stocks, units or equations read from the diagram (system dynamics proper).
- Any change to DISL, DID, FBL, ATD or the causal loop diagram's definition.
- Hosting or sharing the page anywhere; the person decides what to do with the file.

## Verbatim Constraints

- `Export flow page`: the button's label.
- `Backlog`, `Pressure`, `Throughput`, `Level`: the heatmap readings, in that order.
- `.html`: the page's extension.
- 0 to 1: a variable's level; 0.5: its start.
- Seven: the most series the chart starts with.
