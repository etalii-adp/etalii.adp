# Research: FBL 0.10, What the C4, Databricks and Wardley Map Conversions Wait On

Every decision below settles something the specification leaves to the plan. The observations are at etalii.adp `2098cbd`, etalii.adp.ide.standalone `ad1a4680a`, etalii.adp.ide.desktop `eb0492b`, etalii.adp.ide.vscode `3d0d482`, etalii.adp.ide.intellij `4b2c7f3` and etalii.adp.ide.notion `dfadec3`, all `origin/develop` on 2026-10-29. The construct names are the plan's (the specification leaves them to it); the shapes are in [contracts/](contracts/) and [data-model.md](data-model.md).

## R1. How the feature is delivered in etalii.adp

- **Decision**: three pull requests, one per user story, each a version of its own in the order they merge (FR-030: "each later one is the next minor version"). PR A is User Story 1 with the constructs Stories 1 and 3 share (FR-001 to FR-013, FR-023's block written by an add, and FR-030 to FR-037 for what it adds); PR B is User Story 2 (FR-014 to FR-022); PR C is User Story 3 (FR-023's next-line brace, FR-024 to FR-029). A and B are independent and may be written side by side; C starts when A is merged, because it uses A's comments, recovery and absent parts. The first to merge is FBL 0.10; the planned order is A as 0.10, B as 0.11, C as 0.12.
- **Rationale**: one pull request would hold the prose of some twenty-five constructs, two grammars, two new example bindings, about thirty fixtures, the validator's new checks and the ATD rows; it could not be reviewed in one sitting, and Databricks (four waiting tasks, the smallest story) would wait on the C4 work it shares nothing with. Each story is independently testable (the specification says so of each), so each can carry its own document, schema, examples and fixtures, as principle II asks of every pull request.
- **Alternatives considered**: one pull request, all of it as 0.10 (the specification's title; simplest numbering; largest review, and Databricks waits); B first as 0.10 (unblocks Databricks soonest, but the C4 binding, the specification's priority P1, then lands as 0.11 while the stories name 0.10). The choice is put to the maintainer as the plan's first open question.

## R2. Lark and LALR(1): which implementation each place uses

- **Decision**: a host that implements the `grammar` family builds and runs the binding's grammar with its language's EtAlii Lark package (the maintainer's rule of 2026-10-23, as amended 2026-10-24 in spec 035, R9): the standalone library with `EtAlii.Lark` (NuGet, 0.4.0 published), the desktop host with `etalii-lark` and `etalii-lark-derive` (crates.io, 0.4.1, already its dependency since spec 035 T148), Visual Studio Code and the Notion add-ons with `@etalii/lark` (npm, 0.4.0 published). No host writes a table builder, lexer or parser of its own. etalii.adp's own scripts keep Python Lark 1.3.1 (`requirements-atd.txt`), which is the reference the three ports are checked against by their shared conformance suite; there is no EtAlii package for Python and none is needed.
- **Rationale**: the rule's purpose is one verdict on a grammar everywhere. Python Lark is that verdict's source, so the repository that states the grammars checks them with it.
- **Observed gap**: no EtAlii Lark package exists for the JVM, so IntelliJ cannot take the family up under the rule as it stands. IntelliJ binds neither format today (its `CLAUDE.md`: the `fbl` module is "used by no tool yet"), so FR-037 does not reach it now; the feature that makes IntelliJ bind Structurizr DSL or `.owm` has to settle it. Recorded in the plan's host table, not answered here.

## R3. The Structurizr DSL grammar

- **Decision**: `specifications/fbl/structurizr.lark`, beside the rewritten `structurizr.fbl`, in ATD grammar notation, built in strict LALR(1) by `atd-grammar.py --bindings` like `w3c-turtle.lark`. Its shape:
  - **Line ends are tokens.** `_NL: /(\r?\n[ \t]*)+/` ends a statement, and `%ignore` takes only horizontal whitespace and the three comment terminals. Structurizr DSL is line-oriented: without line ends as tokens, `autoLayout` followed on the next line by `title "x"` is ambiguous at one token of lookahead.
  - **Comments**: `LINE_COMMENT: /\/\/[^\r\n]*/`, `HASH_COMMENT: /#[^\r\n]*/` and `BLOCK_COMMENT: /\/\*([^*]|\*+[^*\/])*(\*+\/)?/`, all ignored. The block comment's closing is optional, so a block comment that is never closed is one token to the end of the body (R7), and the longest-match rule of ATD section 3.6 keeps a quoted `"a // b"` a string, since the string terminal starts first.
  - **Positional arguments are rules named by position.** `person: [ident "="] PERSON name [description [tags]] extra* [block]`, where `name`, `description`, `technology` and `tags` are one-token rules (`?`-less, so that each is a node a selector names). Nested optionals read as Structurizr reads them and give each position a node of its own, which a slot then selects (`{"node": "technology"}`). `extra*` takes the further arguments finding B6 lists (a deployment node's instance count).
  - **Arguments are quoted or bare** (`ARG: STRING | WORD`, finding B6's `person User`), and **keywords are matched in any case** by their patterns (`PERSON: /[Pp][Ee][Rr][Ss][Oo][Nn]/`), since the notation has no flags; `w3c-turtle.lark` does the same for `PREFIX`.
  - **A block is `"{" _NL statement* "}"`** after a statement, so the grammar alone decides which statements open one (FR-003). Every element kind the module reads (finding B1's eight), `group`, `deploymentEnvironment`, the relationship forms of finding B8 (with and without a source, opening a block or not), `!`-directives as one generic `directive` statement (`!include` kept and never followed, B11), the view kinds with their optional scope, environment, key and description (B2), and the view statements of B13 (`include`, `exclude`, `title`, `autoLayout`, the separations, a dynamic view's interactions).
- **Rationale**: FR-031 and the Assumptions: the binding reads every workspace the C4 tool reads today, lenient spellings included, and an LALR(1) grammar that cannot read one is a recorded gap, not module code.
- **Checked when it is written**: the grammar builds with no conflict and no terminal collision (`atd-grammar.py --bindings`), and reads every `.dsl` of the conversion's corpus that the reference reader of R20 is given. A spelling it cannot read is recorded in the C4 companions as a gap (Assumptions), with its fixture.

## R4. The `.owm` grammar

- **Decision**: `specifications/fbl/wardley-map.lark`, beside a new `wardley-map.fbl`:
  - `_NL` as in R3; `COMMENT: /\/\/[^\r\n]*/` ignored. A `//` after a colon is not a comment because the token that starts before it is longer: a URL in a `url(name) [x, y] https://…` statement is a `URL` token `/[a-z][a-z0-9+.-]*:\/\/[^ \t\r\n]*/`, which starts at `h` and so is the candidate the lexer takes there (ATD section 3.6, longest match). FR-001's "`https://` is not cut" is a fixture of this.
  - **Free text runs to the line end**: `title`, `note` and an annotation's text are `TEXT: /[^\r\n]+/` where the state shifts it, so `title A map {` keeps its `{` and opens nothing (FR-003).
  - **A pipeline's block** is `pipeline: PIPELINE name [coords] _NL? "{" _NL pipeline_component* "}"` beside `pipeline_bare: PIPELINE name [coords]`: after the name and an optional line end, `{` shifts and anything else reduces, so both brace forms read in one body (FR-023, Wardley map gap 1).
  - **A component's trailer is `segment*`**, `segment: label | decorator | inertia | url_ref | evolve_ref`, so `label [-30, 12]`, `( market )`, `inertia` and `url(name)` read in any order, each a node with its own span (FR-024). The lenient spellings of finding B4 (`lenient-trailer.owm`) are alternatives of these rules.
  - **An annotation's positions** are `positions: "[" position ("," position)* "]"` with `position: "[" NUMBER "," NUMBER "]"`, or one bare `coords`, so each position is a node with two number tokens (FR-025).
- **Rationale and check**: as R3; the corpus is `examples/example 2/` and the module's `Fixtures/`, every file of which `cli-owm` 0.0.2 certified as real OnlineWardleyMaps input.

## R5. Comments: what owns one, and that every splice keeps it (FR-001, FR-004)

- **Decision**: section 4.9 states, for a comment (an ignored token that holds a character other than whitespace):
  1. A comment that is the first token on its line, and every comment on the lines directly above it with no blank line between, is a **leading comment** of the entry whose first token is the next token after them (section 4.1.1), as in 0.9.
  2. A comment that follows a token on its line is a **trailing comment** of the innermost entry that holds that token. `model { // the model` is the `model` entry's, because `{` is a token of the `model` statement and of none of its children; `container "Web" // c` is the container's. A trailing comment is part of that entry's line span, and of no value's span.
  3. A comment that **opens on one line and closes on a later one** is owned by rule 1 when it starts its line and by rule 2 when it follows a token; the owning entry's line span then runs to the end of the comment's last line. Nothing inside it is a token, so it holds no statement, element or brace.
  4. A comment inside a value's span (`"a" /* x */ "b"` read by one slot) is part of the value's text; a set of that value replaces it with the rest of the span, so a binding that reads such a value **SHOULD** use `match` to take one token. The fixture `structurizr-comments` shows that the C4 binding never reads one.
  5. Every splice keeps a comment it does not remove: a `replace-value` changes only the value's span; a value written where it was absent (R6) is written right after the last token before its place, so before a trailing comment; a removed entry takes its leading and trailing comments with its line span.
- **Rationale**: these are the rules the `lines` family already has (section 4.6), carried to tokens, so a host has one notion of ownership; rule 2's "innermost entry that holds that token" is what puts the comment after a brace on the block's opener (scenario 1).
- **Alternatives considered**: a comment owned by the entry below it on the next line (the C4 module's reading of `model { //`; rejected by scenario 1); a binding-level property naming the comment terminals (unnecessary: an ignored token that is not whitespace is already a comment in 0.9).

## R6. Reading in part inside blocks (FR-002, FR-004)

- **Decision**: `body.recover` gains `nested`, `{ "open": "{", "close": "}" }`, the two terminals that open and close a block (each a terminal of the grammar or the text of an anonymous string terminal, as `sync` entries are), and `unclosed`, a map from an ignored terminal to the text it must end with (`{ "BLOCK_COMMENT": "*/" }`). With `nested`:
  1. The reader keeps, for each block it is inside, the parser's state at the last **boundary** in that block: right after the block's `open` token, and after each `sync` token shifted at that depth.
  2. When reading stops inside a block, the text from that block's last boundary is skipped to the end of the first `sync` token that ends after the place reading stopped, lexing with every terminal as 0.9's top-level recovery does; when the skipped text reaches a `close` token at the block's own depth first, the skip ends before it. The parser is restored to the boundary's state and reading continues. The skipped text is unbound and reported once as `fbl.unparsed-text` at the line where reading stopped, as at the top level.
  3. When the body ends inside blocks, each block still open ends at the end of the body: the reader closes it without text, its node's span ends at its last token, and it is reported as `fbl.unclosed-block` at its `open` token's line.
  4. A `close` token that the parser cannot shift and that closes no block is skipped alone, unbound, and reported as `fbl.unmatched-close`; it closes nothing.
  5. A token of a terminal in `unclosed` that does not end with its text is reported as `fbl.unclosed-comment` at its first line; it is still trivia.
  6. An add whose container is a block reported by rule 3 is refused with a reason ("The block is not closed, so nothing can be added to it.").
  Without `nested`, 0.9's recovery stands, and a body that parses as a whole is read as without it (scenario 7, FR-002's last sentence).
- **Rationale**: boundaries after a shifted line end are the places a statement can start again, which is the unit the specification asks to keep and report; a state restore is what an interactive LALR parser offers (Lark's `InteractiveParser.copy`, which the three EtAlii ports carry), so two hosts restore the same state and skip the same bytes (section 6.5). Ending an unclosed block at the end of the body is the specification's (FR-002); ending the skip before a `close` keeps a broken statement from swallowing its block's brace.
- **Alternatives considered**: a pre-pass that counts braces outside strings and comments (the `blocks` family's 4.7 test; it disagrees with the grammar on what a string is, and the contextual lexer cannot be run without the parser); refusing the body when a block is unclosed (0.9 behaviour without `recover`; rejected by FR-002).
- **To confirm in the first host task**: that `EtAlii.Lark` 0.4.0 exposes the interactive parser (`feed_token`, `accepts`, `copy`) and `lex` with ignored tokens kept, as `etalii-lark` does for spec 035's ATD parser. A missing surface is a request to EtAlii.Lark, not code in the host.

## R7. A value written where its node is absent, and removed (FR-006, FR-007, FR-024)

- **Decision**: in the `grammar` family an attribute binding's `create` (section 5.2, today xml's and, with `child`, yaml's and json's) declares an absent part: `{"emit": " \"{value}\"", "after": ["description", "name"], "pad": true}`.
  - `emit` is the part's text, `{value}` the value as written by section 6.3 with the slot's escape (R8).
  - `after` lists, nearest first, the attributes of the same rule whose parts precede this one; the part is written right after the last token of the first of them that is present (so before a block, a trailing comment and anything after it). When none is present the set is refused.
  - `pad: true` makes the part positional: each attribute in `after` before the first present one is written too, with its own `create.emit` and the empty value, nearest last, in the same splice. A part that is present, empty or not, is replaced and never padded again (edge case).
  - The splices are `insert-key` (write) and `remove-key` (clear, with `empty: "remove"`): the part's span and the whitespace between it and the token before it, nothing else. The section 6.1 catalogue lists both for `grammar`, and `absent` and `empty: "remove"` apply as in the other families.
  - **Clearing the last positional part leaves the empty parts before it.** One clear is one `remove-key` of one part; an empty argument written by a user and one written by padding are the same bytes, and the tool cannot tell which to take.
  - FR-007 is a sentence of section 4.9: a set or a written part on an entry that opens a block changes neither the block's opening nor its bytes, which follows from the place rule above; the fixture `structurizr-absent-arguments` shows it on `softwareSystem "S" {`.
- **Rationale**: `create` is FBL's existing name for "how a missing place holding the value is written"; reusing it adds no property. `after` makes the place explicit instead of derived from the grammar's expansions, which two hosts would have to unfold alike.
- **Alternatives considered**: deriving the place from the rule's expansion order (correct, but the order is the grammar's after section 4.4's expansion, which no host exposes); `re-emit-line` (loses unbound words and comments, finding B18).

## R8. Escapes inside a quoted value (FR-005)

- **Decision**: a `{node}` slot takes `escape`, `{"with": "\\", "quote": "\""}`: reading replaces `\"` by `"` and `\\` by `\`, and leaves the escape character before any other character as it is (`C:\temp` reads as `C:\temp`); writing escapes every `quote` and every `with` character of the value. The slot's `match` is applied to the token's text first and the escape to the group `value` it gives; the value span is unchanged. Without `escape`, 0.9's unescaped writing stands. A value that still does not read back (a line break in a one-line string) is refused by the family's re-read check, and nothing is written.
- **To verify while writing the fixture**: that the Structurizr CLI reads `\\` as one backslash, as FR-005 requires FBL to. `C4Interop.Tests.cs` in the standalone host already runs the CLI over what ADP writes; the fixture `structurizr-escapes` is taken from `findings/escaped-quote.dsl`, and if the CLI reads `\\` otherwise, the difference is recorded in the C4 companions and the maintainer is asked before the construct is changed.

## R9. A block written around a first child (FR-023)

- **Decision**: in the `grammar` family an element rule's `opens` is an object, `{"open": " {", "close": "}"}`: when an add with `place: "last-child"` goes into an entry that has no block, the host writes `open` right after the entry's last token and the closing line after the new child, as the `blocks` family's `open-block` does, and the catalogue's `open-block` lists `grammar`. A line feed in `open` writes a line ending and the entry's indentation (the Wardley map's `"\n{"`). A new block written by an `emit` (a new pipeline) is the `emit`'s own text. The existing fixture `structurizr-open-block` then passes under the rewritten `structurizr.fbl` with its input, its splices and its expected bytes unchanged (FR-031), since its splices are already `open-block` and `insert-entry`.
- **Rationale**: FR-031 requires that fixture unchanged, so the grammar family writes the same operations the `blocks` family does.

## R10. Views of a `grammar` binding (FR-008, FR-009, FR-011, FR-012)

- **Decision**:
  - The binding's `blocks` (BlockRule, section 4.7) are admitted in the `grammar` family with `at` instead of `line`: entries that produce no element. `view` names the slot that names the view: a group in `blocks`, a Slot in `grammar` (a `{node}` slot, or a `{value: cel}` slot for the defaults finding B2 lists: a view without a key is `landscape`, its kind in lower case, or its environment).
  - A BlockRule may take `origins` (R12), the readings it is a view for, so that section 9.3's "the first view in document order of the kinds the reading's tool type shows" is stated by the binding: the container reading's views are the `container` views.
  - An element or relation rule with `selectedView: true` reads only the entries inside the entry of the view the registration selects (section 9.3); the same statements inside every other view are not read. With DISL, its type is mapped `as: "diagram"` by `typeMap` (DISL §11.2), as the C4 definitions already map `ViewInclude`.
  - Every view stays an entry of the body read by its BlockRule, so a DISL rule about the model sees every view (DISL's `View`), and an element rule may also select the view's node, without `selectedView`, when the tool type keeps views as elements.
  - A BlockRule may take `insert` (FR-012), with an `emit`, a `place` and a `container`, planned as an element's insert; its `remove` is not added.
  - Section 9.3 names `grammar` views beside `blocks` views, and its last sentence becomes: which elements a view draws is the reading's DISL viewpoint's; what FBL reads of the selected view is the entries of `selectedView` rules (FR-009). A registration whose `view` names no view of the body opens with no view's content, reports nothing, and refuses a change of view data with "This view is not in the document, so its positions cannot be stored." (FR-011).
- **Rationale**: reusing BlockRule keeps one construct for "statements that open blocks and produce nothing" in both families; `selectedView` is the one new bit, the scope test finding B13 asks for.
- **Alternatives considered**: `within: ["view"]` (in `blocks` it means "directly inside any", which is exactly what B13 rejects); views as element rules only (the C4 metamodel keeps views as DISL views, not as element types).

## R11. A read-only value gathered from several places (FR-013)

- **Decision**: in the `grammar` family a read-only attribute binding of a `many` attribute may take `gather`, a list of further `{node}` slots of the same entry, whose values follow the first slot's in document order: `"tags": {"node": "tags", "gather": [{"node": "block/tags_statement/ARG"}], "readOnly": true}`. A binding with `gather` that is not read-only is refused when it is loaded (section 14.1); section 3.3 stays as it is.

## R12. One binding, several metamodels (FR-014, FR-015, FR-016, FR-017)

- **Decision**:
  - Every element rule, relation rule and BlockRule may take `origins`, a subset of the binding's `claims.origins`: the rule is read only for readings of those origins. Section 5.1's "an entry becomes at most one element" holds per reading, so `/resources/pipelines/{pipeline}` is a `PipelineResource` to the bundle reading and the `Pipeline` itself to the pipeline reading, through two rules with disjoint `origins`.
  - `registration.resource` takes `byOrigin`, a map from an origin to `{capture}` or to `null`, beside the existing `capture`: the job reading selects by job key, the pipeline reading by pipeline key, and the bundle reading (`null`) selects none and sees every resource. Section 8.2's default applies per origin.
  - Section 9.1: one open body per path and binding keeps one lossless reading, one history and **one model per origin**; each registration's resource selection is a view of its origin's model. Two registrations of one origin that select different resources share that model and show and edit their own resource; two registrations of different origins share the body and its history, and an edit in either is planned once and shown in both without a reload (FR-015). Section 9.2's read-only rule still applies to a reading whose specification names another binding.
- **Rationale**: `origins` is all in FBL, so DISL does not change (FR-036's permitted `typeMap` value is not used), and a rule's type stays the metamodel's or the `typeMap`'s as today. The specification's "one model, of which each selection is a view" (FR-017) holds within an origin; across origins the models differ because the rules do, which FR-014 asks for.
- **Alternatives considered**: `typeMap` gaining `as: "none"` (a DISL change; leaves a reading with entries it must also tell apart from unreadable ones); relaxing section 9.2 to "compatible" bindings (two bindings over one body would need one history across them, which section 9.1 cannot state simply).

## R13. Inserts into YAML flow sequences (FR-018)

- **Decision**, in sections 4.3 and 6.2:
  - **An empty flow sequence** (`tasks: []`) is opened by a `replace-value` of the value with the whitespace before it (` []`) by nothing, followed by the `insert-entry` of the new block entry under the key, after any comment on the key's line, exactly as the existing fixture `dependency-graph-empty-flow-sequence` records the standalone library writing it; that fixture's `doc` is changed to say FBL now states it.
  - **A one-line flow sequence** (`depends_on: [{task_key: a}]`) takes a new item inside it: one `insert-entry` before `]`, of `, ` and the item, a mapping item written in flow form `{key: value, …}` in `insert.keys` order by section 6.3's scalar rules. Removing an item is a `remove-entry` of the item and one separator, as json's (section 6.2).
  - A flow sequence written over several lines, and a flow mapping, are not one-line containers: an insert into one is refused with a reason (edge cases).
- **Rationale**: the empty case adopts bytes a host already writes and a fixture already records; the one-line case is json's one-line rule (section 6.3), which hosts implement already.

## R14. Refusal sentences, nested mappings, a secondary slot and a lowercased key (FR-019 to FR-022)

- **Decision**:
  - **`refusals`** (FR-019): an attribute binding's `refusals: {empty, absent}` and an insert's `refusals: {when, container}`, each a LocalizedText, the sentence a host shows for that refusal, as `readOnly` gives one (section 3.4). Absent: the host's wording (section 15.3). A fixture's `refused` is then normative for these.
  - **An add writes `child`** (FR-020): an attribute bound with `child` that the add gives a value is written into a mapping the new entry gets, as a set does since 0.4: the level's key at its place in `insert.keys` (or after the keys), then the attribute's key under it, one step deeper, in the same `insert-entry`. `- notebook:` with `path:` below it reads back as the library added.
  - **`secondary`** (FR-021): an attribute binding's second slot, read only when the first slot is absent; a set writes the first slot and removes the secondary (`remove-key`) in the same edit. Its name is not `fallback` (FBL 0.5's value for a slot that does not convert) and it is the reverse of `override`; a binding with both on one attribute is refused.
  - **`{key:lower}`** (FR-022): a template placeholder, `{key}` with ASCII letters in lower case, written in the form `{newid:<rule>}` already has. `My_Job.yml` gives `my_job`.

## R15. The legacy layout (FR-010)

- **Decision**, in section 8.7, for `{base}.layout.json` whatever the body's family:
  - View keys and element keys are both matched with an element's id and a view's key **ignoring the case of ASCII letters**, as `caseInsensitive` matches elsewhere in FBL.
  - When two keys of one view match one id, the first in the file's order applies; the others are neither applied nor written, and each is reported as `fbl.duplicate-key`.
  - Numbers are written as section 6.3's `number: "shortest"` writes them, by json splices: a move is a `replace-value` of `x` and of `y`; a first placement an `insert-entry` of the member, laid out as the view's previous member is (one line, or one key per line), and an `ensure-container` of the view's object when the view has none.
  - **Stale entries are pruned**: an entry of the view being written whose key names no element of the body is removed at that write, in the same edit, as section 8.5 prunes the `layout:` block. The other views of the file are not touched. This is the plan's reason against the specification's default of keeping them: C4's question Q7 was ruled "sidecar entries under such ids are reported and dropped at the next write", and one rule for both stores keeps a host from carrying two.
  - Reading does not round (the module's two decimals, finding B16, are a module behaviour that the C4 conversion keeps or drops under its Q1).
- **Rationale**: FR-010 asks for one form two hosts write alike; every choice here is an existing FBL rule applied to the file.

## R16. Identities: the legacy file, kinds, repeated keys and key changes (FR-026 to FR-029)

- **Decision**:
  - **Section 8.7**: `registration.legacyIdentities` is a JSON array of entries `{"id", "kind", "key"}`, as the Wardley map writes it. An entry is matched to an element by its rule's `sidecar.kind` and the value of its `sidecar.key`. It is read when the registration has no `identities:` block and written back while the file exists, by json splices: a new entry appended as the array's last item, laid out as the item before it; a changed key a `replace-value` of `key`. 0.9 described the file as an object; no binding, example or fixture uses it, and the Wardley map's file has always been the array, so the status paragraph names this as the one place 0.10 gives `legacyIdentities` another meaning.
  - **Section 8.6, kinds** (FR-027): `id.sidecar` takes `kind`, a Name. The `identities:` block keys an entry `<kind>:<natural key>` when the rule declares a kind, and by the natural key alone otherwise (0.9).
  - **Repeated keys** (FR-028): `id.sidecar` takes `ordinal`, the text appended to the natural key of each later holder, with `{n}` its ordinal in decimal (2 for the second), holders counted per kind in document order. The Wardley binding declares `"\u001f{n}\t"`, the form `WardleyIdentityKeys.Numbered` writes today, so every stored file keeps its keys. A later holder's entry is first stored with the next write of the body. Without `ordinal`, 0.9's rule stands: the second holder is reported as `std.duplicateId` and its id is not stored.
  - **Key changes** (FR-029): when an attribute the natural key is computed from changes, the entry is moved to the new key in the same edit (a `replace-value` of the key in the `identities:` block or the legacy file), and an undo moves it back. An id first stored for an element is written with the next write of the body and is no step of the history, as a `history: false` block's writes are (section 7.1).
- **Rationale**: the Wardley map's rulings of 2026-10-11 and 2026-10-12 decide the behaviour; `ordinal` keeps FBL from fixing one tool's key form for every tool while letting that tool keep its bytes.

## R17. Several values from repeated nodes (FR-024, FR-025)

- **Decision**:
  - A `{node}` slot of a `many` attribute reads every node its selector reaches, in document order, each an item; a set writes the difference between the old list and the new, as section 6.3 says for a word slot: `replace-value` of a changed item, `insert-key` of a new one by the slot's `create` (after the slot's last item, or at `create.after`), `remove-key` of a removed one with one separator. This is also how the Wardley map's five decorators read as one set (gap 5 under the grammar ruling).
  - A `{node}` slot may take `items`, a map from an item attribute to a `{node}` slot relative to each item node: the slot's value is a list of structured values (`[{"visibility": 0.43, "maturity": 0.49}, …]`). One item's value is a `replace-value` of its own span; an item is added (`insert-key`, its text from `create.emit` with the item's placeholders, after the last item and a `separator`) or removed (`remove-key`, the item and one separator). `separator` is a property of `items`' slot, `", "` by default when the body shows no example.
  - Where a segment stands twice, the first is read and written (edge case), which a `{node}` slot already does (section 5.2, "the first node … in document order").

## R25. Several items in one argument (FR-038, amendment of 2026-10-30)

- **Observed**: the C4 module splits a tags argument at its commas, `C4Parser.SplitTags` at `edbddc92e` being `tags.Split(',', StringSplitOptions.RemoveEmptyEntries | StringSplitOptions.TrimEntries)`, so a piece is trimmed of `char.IsWhiteSpace` characters and an empty one dropped; Structurizr reads a tags argument the same way. `findings/tags-in-block.dsl` holds `tags "Extra, More"`, which FBL 0.12's `{node}` slot read as one item, since a quoted argument is one token of `structurizr.lark` and a slot reads a node as one item (FBL 5.2). Tags are read-only in the tool and in `structurizr.fbl` (`gather`, FR-013), so no edit of the C4 tool writes one today.
- **Decision**: `split`, a text of one character or more, on a `{node}` slot of a `many` attribute and on a slot of `gather`. The slot's value (the group `value` of `match`, else the node's text) is cut at every occurrence of the text; each piece without its leading and trailing white space (Unicode's `White_Space` property, the set `char.IsWhiteSpace` takes off) is an item whose span is those bytes; an empty piece is no item. Escapes are resolved per item after the cut, so the item spans are spans of the body; `split` may not hold a character of the slot's `escape`, so that the cut cannot fall inside an escape. Writing reuses what FBL 0.12 states for a slot's `items`, and FBL 0.7 for a word slot: the difference by the longest common subsequence; a changed item a `replace-value` of its span; a new item an `insert-key` of the slot's `separator` (FBL 0.12's, `", "` by default) and the value after the last item; a removed run taking the separator before it, or, at the start of a node, the text up to the next kept item; a node with no item left removed as a node of an unsplit `many` slot is; a node holding no item taking the new items as a `replace-value` of its value; no node at all written by `create`. `structurizr.fbl` declares `"split": ","` on all nine tags bindings and their gathered slots.
- **Rationale**: it is the smallest construct that answers the gap and stays general: one property, one text, no new splice operation, no new default, the writing rules those of `items` and word slots. Only commas cut, as the tool and Structurizr cut, and the trimming is the tool's, so the readings agree byte for byte on what an item is.
- **Alternatives considered**: a regular expression for the separator (more general, but the white space around an item would then be the expression's to state, every host would have to agree on its matches, and no format of the corpus needs it); a `split` on every family (the `yaml`, `json` and `xml` families would each need their own writing rules for a value inside a scalar, and no tool needs them); `items` with a sub-grammar over the token's text (a second parser inside a token, for what a cut does); leaving the gap open or accepting FBL's one-tag reading, which the ruling of 2026-10-30 rejected. The one design choice the ruling left open, what a set does to a node whose every item it removes, is settled as the unsplit `many` slot does, by removing the node with the white space before it, so that no empty argument is left behind and no new rule is needed; a binding whose argument is positional and followed by others does not make such a slot writable.

## R26. A member added to a mapping (FR-039, amendment of 2026-10-30, pending the maintainer's card)

- **Observed**: databricks-disl-fbl task 12, writing the bundle through `databricks.fbl`, found that a resource cannot be added: the standalone library refuses with "The /resources/jobs of this file is not a list a Resource can be added to.", since an insert of FBL 0.13 adds an item to a sequence (6.2) and states nothing for a mapping, while a bundle's jobs and pipelines are the members of the mappings `resources.jobs` and `resources.pipelines`, each named by its key. The module's `BundleWriter.AddResourceSkeleton` at `edbddc92e` writes a new job after the last job with a starter task, creates `resources:` when the file has none, and (finding B11) wrote a missing kind directly under `resources:`; the conversion's question Q1 defaulted to what FBL writes.
- **Decision**: no new insert property. A rule of the `yaml` or `json` family whose `at` ends in a `{c}` segment already reads a mapping's members by key, so its `insert` adds a **member**: the key is the value the add gives the attribute bound to `{capture: c}`, taken as the new entry's key and not as a set of the attribute, so the `readOnly` that refuses a rename does not refuse the add; it is written as section 6.3 writes a new string value, the value one indentation step deeper holding the entry's `keys`, constants and `skeleton`. `place` keeps its meanings, `after-last` being after the rule's last member (B11's "a new job follows the last job"); a missing container is created by FBL 0.4's missing levels, a missing kind at the end of `resources` (Q1's default); a key alone (`jobs:`) takes a block mapping; flow form (`jobs: {}`) takes no insert. A missing, empty or duplicate key, compared as written text, is refused with two new sentences, `refusals.key` and `refusals.duplicate`, beside FBL 0.10's. The add is `ensure-container` splices and one `insert-entry`; the removal is the entry's line span, `remove.container` deciding an emptied container. The same rules hold for a `json` object, with `,` separators. A rule with such an insert must bind its key's capture, which section 14.1 checks.
- **Rationale**: the smallest construct that answers the gap and stays general: no new property beyond two refusal sentences, no new splice operation, no new default; it reuses `at`'s capture, `place`, `create`, `skeleton` and `remove.container` as they are, and covers JSON objects by the same text.
- **Alternatives considered**: an `insert.key` naming the attribute that gives the key (redundant with the capture, and a second way of saying it); an `insert.mapping: true` flag (says what the `at` already says); a new splice operation `insert-member` (the bytes are an `insert-entry`'s, and every host already replays those); placement by sorted key order (no format of the corpus sorts its resources, and the module does not); leaving the module to add resources itself, which is the answer were the card's ruling no. The one fork left open, a skeleton written in yaml text for a `json` body, is the existing limit of `skeleton` (6.2) and not changed here: `insert-member-json` writes its member from `keys` and constants alone.
